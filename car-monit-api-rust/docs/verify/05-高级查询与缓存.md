## 3. Redis 缓存隔离对比（Java DB0 ↔ Rust DB1）

`tools/v2/cache_probe.py` 的结果（`.run/verify2/cache_probe.json`）：

| 观测项 | Java DB0 | Rust DB1 |
|---|---|---|
| 键总数（跑测量前） | 4467 | 1021 |
| 键空间构成 | detection 3098 / reliability 900 / car_history_trail 185 / car_sync_time 185 / login_tokens 74 / 其余业务字典各 1 | reliability 900 / sys_dict 59 / sys_config 11 / detection 35 / 各业务字典 1 |
| `car_list_jc` | 存在，187 条，FastJSON 文本（`[{"@type":"com.ruoyi.base.domain.CarVO",…}]`），其中含上一轮校验残留的 `PARITY_carNo_uid*` 伪车牌 | 存在，185 条，同为 FastJSON 兼容文本（说明 Rust 的写入格式与 Java 可互读） |
| 字典键（station_info/gantry_ip/station_ip/dev_post/section_road_map/gantry_list） | 全部存在，值是 Java 序列化文本 | 由 Rust 自己回源重建（`/base/sysutilTest/syncBaseInfo` 实测各 +1 键） |

关键结论与做法：

1. **隔离是必要的，也证明了可对比性**。两端写的是各自的 DB，键名同名但内容互不干扰；
   直接比 `carTrackQueryByTime` 会因为「名单内容不同」得到不同行数，与代码无关。
2. 为了做**公平比对**，把 DB0 的 `car_list_jc` 原文复制进 DB1（先备份 DB1 原值，跑完还原），
   两端处理同一份 187 条名单，此时 5 个 `carTrackQueryByTime` 变体全部逐字节一致：

   | 用例 | 结论 |
   |---|---|
   | `carTrackQueryByTime`（默认分页） | PASS |
   | `?pageSize=3` / `?pageSize=10&pageNum=2`（第二页） | PASS |
   | `?flag=ybn` | PASS |
   | `?startTime=2025-09-30 00:00:00&endTime=2025-10-01 00:00:00` | PASS |

3. **冷缓存分支**：把 DB1 的 `car_list_jc` 临时置成 `[]`，Rust 走 Java 同一道守卫
   （`SysUtilController.java:128` 的 `if (null != carlist && carlist.size() > 0)`），
   返回 `{"total":0,"rows":[]}` 而不是报错 ✓（Java 侧代码同构，因不能清 DB0 的键，故用「只清 Rust 侧 + 代码核对」的方式验证）。
4. 残留差异（不影响接口契约）：
   - Java 的 `login_tokens:*`（74 个，RuoYi 会话）与 `detection:report:*` 由 Java 独有链路产生；
   - Rust 的 `sys_dict:*`/`sys_config:*` 是 Rust 侧字典/配置缓存命名空间，Java 侧对应键在 DB0 里由别的进程写过，
     因此两边键数不可直接比较 —— 这是隔离设计的目的，不是缺陷。
   - 上一轮校验脚本在 DB0 留下的 `PARITY_carNo_uid*` 伪车牌仍在 `car_list_jc` 里（187 条中的 2 条）。
     本轮没有改动 DB0（只在 DB1 里做过备份/还原），如需清理要单独确认。

异步任务状态复核（各端查自己的 taskId）：

```
large/export/status   → 双端 keys 相同（code,status,totalExported,filePartCount,submitTime,endTime），都是 FAILED
unified/export/status → 双端 keys 相同（多出 errorMessage），都 FAILED（本机 ES 索引不可用）

```

导出目录：`D:\data/export/<taskId>/` 双端都创建了任务目录（配置项 `optimization.export.dir=/data/export`）。

## 5. 写端点的结论

- 状态码与响应体：20/20 与 Java 一致（其中 `syncOdsSzdnGantry` 的 500、`sync/repair` 的 400 都是**刻意复刻的错误**）。
- 副作用：`syncBaseInfo` / `syncHistroyTrack` 在 Rust 侧是**真实执行**的（刷新 DB1、写 370 个键）；
  之前 Rust 代码里对 `syncSuspiciousCarN` / `separateSnapshotFlowTimeList` 的「不执行」注释仍然成立——
  这两个在 Java 侧同样不产生业务写入，因此不构成行为差异。
- 唯一残留差异是异步任务失败时的 `errorMessage` 文案（Java 透出 ES 原始异常，Rust 是自己的中文包装），
  两端 `code`/`status`/键集合一致，属可接受差异。
