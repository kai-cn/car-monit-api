# 阶段10 · 性能与稳定性

> 同一台机器、同一个 GaussDB（`192.168.56.10:55432/RuoYi`）、Redis DB0(Java) / DB1(Rust) 隔离。
> 时间都是 harness 里 `http_get` 的端到端耗时（含 SQL、序列化、网络回环），单位 ms。

## 1. 起点：`carTrackQueryByTime` 慢 Java 一个数量级

阶段5/6 记录的性能差异项，本轮开始时的实测（debug 构建、逐行重建字典）：

| 用例 | Java | Rust | 倍数 |
|---|---|---|---|
| `sy:byTime:00` | 2477 | 6429 | 2.6× |
| `sy:byTime:05` | 2425 | 6173 | 2.5× |
| `sy:byTime:06` | 2417 | 5877 | 2.4× |
| `sy:change:04-real` | 1900 | 1162 | 0.6× |

阶段6 报告里写的「Rust 3.9s vs Java 0.26s」是同一端点另一组参数的单次观测。

原因分三层，按影响从大到小：

1. **一页里逐行重建 5 张字典映射**。`build_trail_infos()` 对每一行都调 `change_data()`，
   而 `change_data()` 内部会 `station_ip_map() / toll_map() / gantry_ip_map() /
   location_map() / section_map()` 各来一遍。这些映射是把 Redis 里的整表 JSON
   现场搭出来的（`gantry_ip_map` 每行数据要插 ~9 个键），10 行数据 = 50 次全量反序列化。
2. **`dev_post` 缓存「写得进、读不出」**。`serde_json` 开了 `arbitrary_precision` 之后，
   JSON 数字不再走 `visit_f64/visit_u64`，而是包成单键 map；`JDecimal`（以及 `JInt/JLong/JFloat`）
   的 visitor 没接这个形状，于是每次读缓存都报
   `invalid type: map, expected BigDecimal 数字或数字字符串 at line 1 column 392`
   → 回源查全表 → 再写一遍缓存 → 下次还是读不出。日志里这条 WARN 每个请求刷一次（883KB blob）。
3. **跑的是 debug 构建**：serde 反序列化、`String` 大量 clone 这类代码，debug 比 release 慢 3–8 倍。

## 2. 做了什么

| 改动 | 位置 | 说明 |
|---|---|---|
| 字典映射改为**请求内复用** | `src/services/dict.rs::DictService::bundle()` + `DictBundle`；`services/sysutil.rs::build_trail_infos/change_data/change_data_with` | 一次请求构造一次，`change_data_with()` 接收快照。**不是 TTL 缓存**：每个请求仍然照常读 Redis，否则「双端 DB 隔离 → 缓存内容不同 → 结果不同」这条对比链路会被破坏（阶段5 的缓存实验依赖它） |
| 数值包装类型接住 `arbitrary_precision` 的数字表示 | `src/models/mod.rs`，`JInt/JLong/JFloat/JDecimal` 各加 `visit_map`（`tools/v2/patch_raw_number.py` 可重放） | 缓存回读恢复；`dev_post` 不再每次回源。顺带修掉一个潜在契约洞：POST 体里给 decimal 字段传 JSON 数字（而非字符串）也会踩同一个反序列化失败 |
| `weight_capture_map` 用 `BTreeMap` | `src/services/sysutil.rs` | 响应 `data` 的键顺序不再随机（详见 §4） |
| release 构建与脚本 | `tools/v2/rust_restart_release.sh` | 与 `rust_restart.sh` 同参数，只是跑 `target/release/`，用于性能对比 |

## 3. 结果

改完（release + 上面三项）后，`sysutil` 全 59 例逐条合计 **Java 2351ms / Rust 2236ms（0.95×）**：

| 用例 | 改前 Rust(debug) | 改后 Rust(release) | Java |
|---|---|---|---|
| `sy:byTime:00` | 6429 | 127 | 381 |
| `sy:byTime:05` | 6173 | 211 | 362 |
| `sy:byTime:06` | 5877 | 233 | 379 |
| `sy:byTime:01` | 2760 | 265 | 170 |
| `sy:change:04-real` | 1162 | 192 | 18 |
| `sy:change:07-with-dec` | 1165 | 168 | 25 |

单独计时（同一用例连打 4 次取稳定段）：`sy:byTime:00` Rust 110–166ms（Java 375–1377ms，
Java 这边受 JIT/GC 抖动更大），`sy:change:04-real` Rust 81–85ms（Java 31–33ms）。

结论：
- 分页轨迹查询（`carTrackQueryByTime`）**已与 Java 同量级，多数样本反超**；
- `changeData` 单点富集仍有 ~2.5× 的绝对差距（80ms vs 32ms），成本是「一次请求重建
  5 张映射」：读 ~2.3MB Redis blob（`dev_post` 883KB + `gantry_ip` 809KB + `station_ip` 346KB +
  `station_info` 308KB + `section_road_map` 25KB）、反序列化 ~3300 个实体、插 ~14000 个 map 项。
  Java 是「按点取键、命中即用」，不需要整表搭映射。
  进一步压缩要改成「按 `stateType` 只搭需要的映射 + map 值用 `Arc<T>` 免去 clone」，
  属于独立优化，本轮没做（不影响契约）。

全量耗时对比（每轮 8 并发，双端各打一遍，含网络与 SQL）：

| 阶段 | 例数 | Java 合计 ms | Rust 合计 ms | 比值 |
|---|---|---|---|---|
| base | 1024 | 55533 | 33605 | 0.61 |
| filters | 2349 | 77773 | 71782 | 0.92 |
| filters2 | 8894 | 199802 | 235794 | 1.18 |
| dates | 1353 | 25094 | 32041 | 1.28 |

绝对值是每例 +1~2ms 的量级。

## 4. 稳定性（阶段11）

工具：`tools/v2/stability.py`。同一请求连续打 5 次，分别检查

- 单端自稳定：去掉易变字段（`id/uuid/timestamp/taskId/...`）后逐字节一致，
  **键序与数组序仍然敏感**（顺序抖动要能被抓到）；
- 双端逐次一致：第 k 次的 Java 与 Rust 相同。

样本 275 例 × 5 次 × 2 端（覆盖 8 个阶段的各个分组）：

| 结论 | 数量 |
|---|---|
| PASS（两侧各自稳定 + 每次逐字节一致） | 270 |
| Rust 自身抖动 | **0** |
| Java 自身抖动 | 1（`ct:acc07-2`，Smile 二进制里嵌了 epoch 毫秒，属 D2） |
| CROSS-DIFF（各自稳定但两侧内容不同） | 3（`gap:weight-map*`，见 `09` 的 D1） |
| ACCEPTED（二进制编码，不做字节判定） | 2 |

过程中唯一一次真实的 Rust 抖动，就是 `data` 键序随机（`HashMap` 迭代序），
已经通过 `BTreeMap` 修掉：修前同一请求交替出现两种顺序，修后与 Java 完全一致。

```json
// 修前，tools/v2/map_order_probe.py 实测
rust: [['7379e7aa-…','18f8e2af-…'], ['18f8e2af-…','7379e7aa-…'], ['18f8e2af-…','7379e7aa-…'], ['7379e7aa-…','18f8e2af-…']]
// 修后
rust: [['18f8e2af-…','7379e7aa-…'], …4 次全同…]   == java
```

## 5. 复跑方式

```bash
cd car-monit-api-rust
bash tools/v2/rust_restart.sh            # 日常：debug
bash tools/v2/rust_restart_release.sh    # 性能对比：release（参数完全相同）

python tools/v2/stability.py --repeats 5 --per-stage 8 \
  --from base,gap,query,sysutil,contract,filters,dates,filters2
python tools/v2/map_order_probe.py       # data 键顺序
python tools/v2/map_cache_roundtrip.py   # D1 取证（只动 DB1，跑完还原）
python tools/v2/same_input.py            # 同输入公平比对（只动 DB1，跑完还原）
```

注意：`run.py --stage a,b,c` 会把结果写成 `a+b+c.jsonl` 这一个文件；
要做逐阶段统计就按阶段分别跑（本轮的正式数据就是逐阶段跑的）。
