契约层的口径：HTTP 状态码、Content-Type、响应体结构（键集合/类型/数字与日期的序列化文本）

## 2. 已知可接受差异（不计为失败）

| 差异 | 说明 |
|---|---|
| `Accept: application/cbor` / `application/x-jackson-smile`（8 例） | Java 的 Spring Boot 自动注册了 CBOR/Smile 消息转换器，会按 Accept 输出**二进制**；Rust 侧统一输出 JSON。状态码一致，Content-Type 与字节不同。这两个编码在本系统的任何调用方（前端/网关/压测）里都没出现过，实现二进制编码器属于为不存在的消费者付代价，故记录为差异。 |
| Tomcat HTML 错误页 vs Spring JSON 错误体 | 超长请求行（>8075 字节）等容器级拒绝，Java 返回 Tomcat 的 HTML 400，Rust 返回 Spring 风格 JSON 400；状态码一致。harness 对「同状态码 + Java 侧 text/html」的组合判为 `ACCEPTED`。 |
| `/healthz` `/readyz` `/health` | Java 未接 Actuator，Rust 新增；只读、无副作用。 |

## 3. 值得记住的 Java 侧事实（写进迁移基线）

1. `server.port=9901` 是 Java `application.yml` 的值，本轮为避开本机占用改跑 9902（`-Dserver.port`），
   Rust 用 9911，端口本身不属于契约。
2. Tomcat 的 `maxHttpHeaderSize=8192` 把请求行算在内：`path?query` 长度 8075 → 200，8076 → 400；
   Rust 侧原来就复刻了这道闸门（`MAX_URI_BYTES`），本轮沿用。
3. Spring 对矩阵变量（`/base/gantry/list;a=b`）的处理是「段内分号到下一个斜杠之前」不参与匹配，
   与 `%3B` 编码后的字面分号不同；Rust 归一化后两端一致（该用例通过）。
4. 大小写敏感：`/BASE/gantry/list` 双端都是 404 ✓。
