# 阶段12 · 并发一致性与状态隔离

> 工具：`tools/v2/concurrency.py`（并发一致性）、`tools/v2/stress_accept.py`（accept 层压力）、
> `tools/v2/pagehelper_leak_probe.py` / `pagehelper_leak_scope.py` / `pagehelper_leak_sources.py`（Java 泄漏取证）。
> 机读结果：`.run/verify2/results/concurrency.jsonl`。
>
> **本阶段抓到一个 Java 基准侧的真实缺陷**：`/base/feerecords/*` 的 500 路径会把 PageHelper 的
> 分页参数留在 Tomcat 线程上，导致**后续落在同一线程的其它端点被悄悄截断结果**。Rust 侧结构上不会发生。

## 1. 为什么要单独做并发阶段

前面 14081 例都是「一次一个请求」的比对，验证不了**状态隔离**：

- Java：PageHelper 的 `startPage()` 把分页参数放在 `ThreadLocal`，Tomcat 线程是池化的，
  一个请求留下的残留会影响下一个复用该线程的请求；
- Rust：分页参数每请求从 query 解析（`PageParams`），路径状态用 `task-local`
  （`CURRENT_PATH` / `OriginalPath`），字典映射每请求重建（阶段10 的 `DictBundle`）。

做法：先**串行**取每个用例的基线，再把（用例 × 双端 × 轮次）混在高并发里打，
每个响应都必须等于自己的基线。样本里刻意包含 33 个自造形状：同一端点、
不同 `pageNum` / `pageSize` / `orderByColumn` / `reasonable` 交错 —— 这是 ThreadLocal
串味唯一能被观察到的形状。

## 3. accept 层压力（排除「服务被打死」的怀疑）

第 1 轮探针曾出现「进程还在但 9911 不再监听」。用 `stress_accept.py` 做了受控复现：

```
20s、32 并发疯狂新建连接 + 16 条只连不发的空闲 keep-alive：
  成功 17107，失败/超时 2692（自带 8s 超时，属自伤），最慢 324ms  →  ~890 req/s
  16 条空闲长连接全部建立成功
压测后立刻串行 10 次 /healthz：全部 200、0ms
日志「请求完成」增量 19809 ≥ 成功数 → 服务端确实在处理，accept 循环没有死
```

结论：**不是被测代码的问题**。那次「消失」是工具超时把后台命令的进程树连带杀掉，
`nohup` 起的 Rust 服务正好在同一棵树里；而探针当时用的是 120s 超时，
在服务已经没了之后逐个空等 88 次 ≈ 永不结束。已给 `concurrency.py` 加了：

- `preflight()`：双端 3s 内必须可应答，否则直接退出并说明原因；
- 默认超时 120s → 20s。

## 4. Java 侧 PageHelper 残留（本阶段的核心发现）

### 4.1 泄漏源

`BaseController.startPage()` 在**方法体第一行**就把分页参数塞进 ThreadLocal
（`pro-base-common/.../BaseController.java:53-56` → `PageUtils.java:25`
`PageHelper.startPage(pageNum, pageSize, orderBy).setReasonable(reasonable)`），
正常由紧随其后的 MyBatis 查询消费并清除。`/base/feerecords/list|listToExport` 没有对应的 Mapper XML
（阶段3 已确认：接口声明 5 个方法，XML 里只有 `selectByCursorShard`，缺 4 个 id），
MyBatis 在 `MapperMethod` 构造期就抛 `BindingException`，拦截器从未运行 →
**页面留在池化线程上**。框架其实提供了 `BaseController.clearPage()`（`:74-77`），
但全项目 Java 代码没有任何调用点，也没有 `try/finally` / Filter / Interceptor 兜底。

受害者用 `/base/gantry/listAll`（经 MyBatis、自己不分页，本机全量 1526 行）与
`/progressive/snapshotflow/list?pageSize=`（同形状，全量 900 行）：

| plant（制造残留的请求） | plant 状态 | 受害者被截断 | 判定 |
|---|---|---|---|
| `GET /base/feerecords/list?pageSize=2` | 500 | 会截断（`listToExport` 那一轮 8/8） | **泄漏源** |
| `GET /base/feerecords/listToExport?pageSize=2` | 500 | **8/8** | **泄漏源** |
| `GET /base/toll/list?pageSize=2&orderByColumn=1;drop table x` | 500 | 0/8 | 干净（orderBy 在拦截器里校验，页面被正常清除） |
| `GET /base/toll/list?pageSize=2&orderByColumn=<600 字符>` | 500 | 0/8 | 干净 |
| `GET /base/feestationexit/list?pageSize=2&feerate=<40 位数字>` | 200 | 0/8 | 干净 |
| `GET /base/gantry/list?pageSize=2`（正常分页） | 200 | 0/8 | 干净（自我消费） |

> 更正：早先一版把 `GET /base/feerecords/1`（详情 500）也算作泄漏源（当时测到 3/8）。
> 复查代码后确认 `getInfo()` 里**没有** `startPage()`
> （`OdsLwzxsfsjFeeRecords01Controller.java:201-203`），它只是另一个会失败的接口 /
> 被动受害者；那 3/8 来自当时线程上已有的其它残留。
> 另外「同连接紧邻才触发」的概率非常受线程调度影响（隔天用同样脚本复现出过 0/8），
> 所以下面 §4.2 改用「批量铺残留再测」的不依赖运气版本。

Rust 侧同一清单每轮 3 次、共 21 轮，受害者**恒 1526 行**，一次都没有被截断。

### 4.2 概率化复现（`pagehelper_leak_repro.py`，2026-11-04 复测）

不依赖「同连接恰好同线程」：先在 30 条连接上各发一次 plant（往多个 worker 线程铺残留），
再连续两轮各测受害者 30 次。

```
[java] 阶段0 基线（全新连接 30 次）           : {900: 30}
[java] 阶段1 铺 30 个 /base/feerecords/list?pageSize=2 : 全部 500
[java] 阶段2 立刻测受害者（30 次）            : {2: 10, 900: 20} → 被截断 10/30（33%）
        被截断响应的 (status, rows, total)    : (200, 2, 900) ×4 抽样
        ↑ total 仍是全量 900，只有 rows 变少，客户端与监控都看不出异常
[java] 阶段3 再测一轮（30 次）                : {900: 30} → 0/30（残留被逐个消费掉，故障自愈）
[rust] 同样四阶段                             : {900: 30} / 0/30 / 0/30，全程无截断
```

`pagehelper_leak_scope.py`（同连接紧邻的 A/B 对照）：

- A) `plant → watch` 紧邻，10 轮：`watch` 行数分布 `{2: 7, 900: 3}`；
- B) `plant → 另一个自带 startPage 的请求 → watch`，10 轮：`{2: 8, 900: 2}`
  —— 中间那个请求虽然在自己的线程上消费了自己的页面，但**残留是线程级的、跨连接可见**，
  Tomcat 把 `watch` 调度回被污染的线程时照样被截断；
- 反向对照（先 `watch` 再 `plant`）不受影响。

被截断时 `total` 仍然是正确的全表计数（PageHelper 的 count 查询不受残留影响），
所以响应看起来「合理」——`{"total": 900, "rows": [2 条]}`，**只在数据变少上露馅**，
这类缺陷靠单请求比对是抓不到的。

### 4.3 为什么 Rust 不复刻

Rust 的分页参数来自当次请求的 query（`PageParams`），执行方式是给 SQL 加 `LIMIT/OFFSET`，
没有跨请求的线程状态可泄漏。要严格复刻 Java 的这个行为，等于在 Rust 里实现一个
「线程池残留分页参数」的缺陷，且它会让 Rust 在并发下变得不可复现——
与校验目标（同请求同结果）相反。因此判定为 **Java 基准缺陷，不修**，
建议 Java 侧的修法是 `feerecords` 的两个 Mapper 补 XML（或去掉那两条路由上的 `startPage()`），
以及全局上把 `startPage()` 放进 `try/finally { PageHelper.clearPage(); }`。

## 5. 与既有结论的关系

- 阶段3 记录过 `/base/feerecords/*` 恒 500（`F28`），当时只当作「缺 Mapper XML 的行为差异」，
  本阶段进一步发现它还会**污染同线程的其它查询**；
- 阶段3a 的分页矩阵（24 例）与阶段9 的 `dates-range` 都是单请求验证，全部仍然成立；
  本阶段说明：**要在并发下守住 parity，必须每请求重新解析分页参数**，Rust 已经是这个模型。
