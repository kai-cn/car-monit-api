## 0. 结论摘要

**一句话：迁移的“形状”已高度对齐，但“运行时”尚未对齐。作为行为对照参考实现质量很高；作为生产替换，当前不可上线。**

| 维度 | 结论 | 依据 |
|---|---|---|
| HTTP 接口面 | **100% 结构覆盖**：24 Controller / 85 handler 全部注册，0 缺失、0 签名不一致、0 重复映射 | 【实测】`tools/check_routes.py`、`tools/_out_audit.txt` |
| 文件对照面 | **100% 文件覆盖**：219 个 Java 文件一一对应；另有 2 个 Python 专有基础设施文件 | 【实测】文件集 diff（见 §2.1） |
| SQL 真实性 | **真实执行**：22 个 XML / 54 条 statement / 58 个方法绑定到 SQLAlchemy + psycopg，直连 GaussDB | 【实测】`/base/gantry/list` 返回 `total=1526`；`/base/gantry/18` 正常 |
| 中间件真实性 | **几乎全为进程内替身**：Kafka/Pulsar 假成功、ES 内存索引、Redis 内存 + 只读穿透、JdbcTemplate 空转、Forest 假 200 | 【静态】+【实测】`check_middleware` |
| 启动生命周期 | **缺 Spring 组件生命周期**：至少 2 个 `@Service#@PostConstruct` 的后台线程在 Python 侧从未启动 | 【静态】+ 实例化检索 |
| 事务 | **无事务管理器**，每条 SQL 独立事务 | 【静态】`app/db/engine.py:199-203` |
| 测试有效性 | 83 个用例**全部是基础设施/框架层**；业务逻辑断言散落在根目录 `_smoke_*.py`，未进 CI；无覆盖率工具 | 【实测】+ 文件阅读 |
| 现有门禁 | **两条门禁是红的**：`check_parity` exit 1、`smoke_all_routes` exit 1；`check_env` 的检查清单与 `requirements.txt` 不一致（本机因 venv 多装了包才通过） | 【实测】§1.2 |

### 0.1 阻断上线的 6 个问题

| 编号 | 问题 | 影响 |
|---|---|---|
| **B1** | Python 服务运行时依赖 `../pro-business-api` 的 Java 源码树来加载 Mapper XML | 只发布 Python 目录 → 22 个 XML 全部丢失，Mapper 静默退回“移植期臆造实现”或抛异常 |
| **B2** | Kafka/Pulsar/ES/Redis/JdbcTemplate/Forest 均为进程内替身，写操作“假成功” | 数据不出进程；多实例各自为政；ES 导出任务实测失败、统一查询退化为 DB 降级路径 |
| **B3** | Spring Bean 生命周期未复刻：`SnapshotFlowSyncService`、`KafkaProducerService` 从未实例化 | Java 启动即跑的“全量/增量同步线程 + Kafka 重试线程”在 Python 中完全不存在 |
| **B4** | 无事务基础设施 | 多语句写入无原子性；Java 唯一的 `@Transactional` 语义无法复现 |
| **B5** | 启动 fail-open：Controller 不可用、Mapper 安装失败、statement 缺失都只记日志 | 与 Spring 的 fail-fast 相反，可能带着残缺路由/映射长期运行 |
| **B6** | 密钥与配置：`application.yml` 明文数据库/ES/RabbitMQ 口令；`/docs`、`/openapi.json`、`/health` 无鉴权暴露 | 凭据入库；生产攻击面扩大 |

### 0.2 生产可用性判断

- **只读接口**：可用性取决于“表是否存在 + XML 是否存在”。门架类接口实测正常；4 个接口恒 500（3 个 fee + 1 个 trailFitting，Java 侧同样缺 XML）。
- **写接口**：85 个 handler 中**没有任何数据库写操作**（`insert/updateById/delete*` 只出现在 MQ 生产/消费服务里），因此 HTTP 面“误写数据”的即时风险较低。
- **异步链路**：ES 导出、统一查询 ES 分支、Kafka/Pulsar 同步链路在当前实现下均不可用于生产。

### 2.6 “死代码”要分两类，不能混为一谈

**A. Java 本身就是死的（Python 忠实保留，不算迁移缺口）**

- `CarTask`、`SparkHiveConfig`：Java 整体 `/* */` 注释。
- `SnapshotFlowPulsarConsumer`、`DebeziumReadonlyPulsarConsumer`：Java `//@Service`，Spring 不会创建。
- `PulsarProducerService`：Java `//@Service`。
- `DataProcessService`：`@Service` 但其消费者不可用，实际无调用方。
- `ProgressiveQueryArchitectureService#esPlaceholder`：Java 原文就返回“空列表 + total=0”的 ES 占位结果。
- 6 个无 XML 的 Mapper 方法：Java 调用即 `BindingException`。

**B. Java 是活的、Python 漏了（真正的行为缺口）**

- `SnapshotFlowSyncService`（`@Service` + `@PostConstruct`）：Java 启动即提交 `fullSync` 与 `incrementalSync` 两个线程（`SnapshotFlowSyncService.java:47-56`）；Python 侧 `init()` 写好了，但**全工程没有任何地方 `SnapshotFlowSyncService()`**（仅 `_smoke_*.py` 有）。
- `KafkaProducerService`（`@Service` + `@PostConstruct`）：Java 启动即起单线程重试循环；Python 同样无人实例化。
- `ElasticsearchQueryService`（`@Service` + `@PostConstruct`）：Java 启动即建 ES 客户端；Python 无人实例化（其唯一调用方 `CompositeQueryOptimizationService` 也未被实例化）。影响较小，但属于同类问题。

> `app/scheduler/registry.py:74-81` 的 `JOB_CLASSES` 只覆盖 6 个定时任务 Bean；`app/main.py` 没有组件扫描，只构造 24 个 Controller（及其构造链）与 6 个调度 Bean。**这是“无 DI 容器”的直接后果，不是某一行代码的疏漏。**

## 3. 迁移质量评价

### 3.1 分层与目录结构

**做得好的地方**

- 目录与 Java 包结构逐字镜像（`com/ruoyi/base/...`），`bootstrap.py` 把 3 个根塞进 `sys.path`，等效 Maven classpath；业务代码的 import 与 Java 几乎一致。
- `app/` 宿主层与业务层分离清楚：`db/` 解释器、`routes/` 分发、`web/` 绑定与序列化、`scheduler/` 调度、`compat/` 生成元数据。
- 每个移植文件都有 `源文件：...` 与 `【Java→Python】关键差异` 说明，可追溯性优于一般迁移工程。

**问题**

| 问题 | 位置 | 级别 | 说明 |
|---|---|---|---|
| 替身层与业务层混放在同一工作区根目录 | `com/ java/ javax/ org/` | 中 | 无法通过 import 边界区分“业务代码”与“仿真层”；替换真实客户端时影响面不可控 |
| 根目录堆积 45 个 `_*` 临时文件与 23.2MB 日志 | 仓库根 | 中 | `_smoke_*.py`（23 个）、`_impl_*.txt`、`_domain_spec.txt` 等共 45 个 `_*` 文件，`py.log` 23.2MB；且部分已入库（`git ls-files` 可查到 `_smoke_t08_kafka.py`） |
| 无 lint / 类型检查 / 格式化 | `pyproject.toml` | 中 | 无 ruff/mypy 配置；28k 行业务代码完全依赖人工审查 |
| 无 Dockerfile / CI / 进程管理 | 仓库根 | 高 | 只有 `run.py`；生产部署方式未定义 |

### 3.2 替身层仿真度与隐患

**总评：单个替身“像”的程度普遍不错，但作为整体系统仿真不成立**——因为替身共享的是“单进程内存”，而不是“外部集群”。多实例、重启、跨语言并行运行三种场景全部失真。

| 替身 | 仿真度 | 具体隐患 | 证据 |
|---|---|---|---|
| `RedisCache` / `RedisTemplate` | 中 | ① 写永远只在进程内，Java/其他实例读不到；② 列表/哈希/集合的 TTL 不生效（只有 `opsForValue` 检查过期）；③ **无锁**：`increment`、`setIfAbsent` 是“读-改-写”，FastAPI 40 线程下会丢更新 | `RedisCache.py:103-127`、`136-331`、`409` |

### 3.3 MyBatis XML 解释器与 QueryWrapper

**结论：当前 22 个 XML 的语法子集覆盖正确，短期正确性风险低；长期风险在“未来新增 XML 特性时静默降级”。**

**数据库连接层是真实的（不是替身）**：SQLAlchemy `QueuePool`（`pool_size=5`、`max_overflow=15`，对应 Druid `maxActive=20`）、`pool_pre_ping=True`、`connect_timeout=10`；【实测】可直连 GaussDB 并返回 1526 条门架数据。缺口在“会话/事务/连接参数”，不在“连接本身”。

已验证正确的点：

- `<if test>` 使用自写 OGNL 子集（`app/db/expr.py`），不是 `eval()`，避免 XML 注入执行任意 Python。
- 动态 SQL 的块拼接采用 `StringJoiner(" ")` 语义；`<where>` 去掉整块首个 `AND/OR`，空块不输出。
- `#{}` → `:p0/:p1` 位置绑定；`<foreach>` 支持 `list/collection/@Param` 名与 `item.index` 作用域。
- 结果映射：先 `resultMap` 显式列，再按 `map-underscore-to-camel-case` 自动映射；未映射列按 MyBatis `PARTIAL` 规则忽略。
- 22 个 XML **实测均无** `${}`、`<selectKey>`、`useGeneratedKeys`、`<association>/<collection>`（扫描结果 0）。
- 所有 statement 在空参数/全条件为真两种极端下都能渲染（`tests/test_phase2b.py`）。

风险点：

| 风险 | 位置 | 级别 | 说明 |
|---|---|---|---|
| `${}` 支持是直接字符串替换 | `xml_mapper.py:284-288` | 中（潜在） | 当前 0 使用；一旦未来 XML 引入 `${}`，就是 SQL 注入面。建议直接禁用并抛错 |
| 未知标签只 warning，按纯文本拼入 SQL | `xml_mapper.py:568-570` | 中 | 例如未来出现 `<bind>` 会被“当作静态文本”，生成非法 SQL 而非启动失败 |
| `map-underscore-to-camel-case`、`call-setters-on-nulls` 配置项未被读取 | `app/settings.py:150-155` | 低 | 行为硬编码为 true；配置改动无效（见 §3.7） |
| QueryWrapper 仅支持 10 个算子 | `com/baomidou/.../LambdaQueryWrapper.py:84-162` | 中 | 无 `or/and/nested/apply/groupBy/having/exists`；当前业务未使用（已全量 grep 确认），但未来 Java 代码新增会直接 `AttributeError` |
| `last("LIMIT n")` 只识别 LIMIT | `LambdaQueryWrapper.py:153-162` | 低 | 其它尾缀（`FOR UPDATE`）被静默忽略 |
| `selectList(<predicate>)` 会**全表读取后在 Python 过滤** | `app/db/base_mapper.py:216-220` | 高（性能） | 真实库上是无界全表扫描；当前只在内存兜底路径使用，需加护栏 |
| BaseMapper 的 schema 只对 2 个实体生效 | `BaseMapper.py:58-70`、`app/compat/java_meta.py` | 中 | `TABLE_SCHEMAS` 仅 `KafkaMessageRecord`、`OdsRtSzdnSnapshotFlowAddcode`；其它实体依赖 `search_path` 或 XML 内写全限定表名 |
| JDBC URL 的 query 参数被整体丢弃 | `app/db/engine.py:90-105` | 中 | docstring 说“只保留 currentSchema”，实际 `partition("?")` 把整个 query 丢掉；若生产依赖 `currentSchema` 解析表，会直接找不到表 |

### 3.4 参数绑定与响应序列化对 Spring 语义的还原度

**已验证一致（【实测】）**

- `@RequestParam` 必填缺失 → 400 + Spring 错误体；类型转换失败 → 400。
- 重复参数取第一个（Servlet `getParameter` 语义）。
- `@RequestParam Map<String,String>` 收到**全部** query 参数，值为字符串（含 `fuzzyFields.xxx` 前缀键）。
- `@RequestBody Map<String,String>` 把数字/布尔转成 `"1"/"true"`；非 JSON Content-Type → 415；空 body + required → 400。
- `AjaxResult` 的 `data` 为 null 时**不输出 `data` 键**（与 Java `StringUtils.isNotNull(data)` 一致）。
- `TableDataInfo` 键顺序 `total/rows/code/msg`；`AjaxResult` 键顺序 `code/msg/data`。
- 无 `@ControllerAdvice` 时 500 走 `BasicErrorController` 形状：`timestamp/status/error/message/path`，`message` 为空串。
- 直接访问 `/error`：HTTP 500 + `status:999 / error:"None"`，无 `path` 键。

**发现的偏差**

| 偏差 | 位置 | 级别 | 说明 |
|---|---|---|---|
| Java `BigDecimal` 被映射为 Python `float` | 7 个 domain 文件中 **39 个字段**（如 `OdsLwzxsfsjFeeRecords01.py:43`）；`app/web/serializer.py:127-129` | **高** | 金额/重量/尺寸字段失真：`Decimal("1.50")` → JSON `1.5`；`Decimal("12345678901234567890.12")` → `1.2345678901234567e+19`。Java 输出是精确十进制文本。**这是可被下游对账发现的契约差异** |
| `@JsonFormat` 带 `SSS` 时输出 6 位微秒 | `app/web/serializer.py:104-114` | 中（潜在） | `strftime("%f")` 后只把 `000000` 替换成 `000`；`microsecond=123456` 会输出 `.123456` 而非 `.123`。当前 14 个 `@JsonFormat` 只用到 `yyyy-MM-dd` 与 `yyyy-MM-dd HH:mm:ss`，属潜在缺陷 |
| HEAD / OPTIONS 返回 405 | `app/routes/registry.py:366-375` | 低 | Spring MVC 对 GET 映射自动支持 HEAD；OPTIONS 返回 200 + `Allow`。实测 Python 均 405 |
| 405 响应缺少 `Allow` 头 | `app/web/errors.py` | 低 | Spring/Tomcat 会带 `Allow` |
| 非 dataclass 对象按 `__dict__` 全量序列化 | `app/web/serializer.py:169-176` | 中（潜在） | 若某个响应对象是普通 Service 类，会把注入的服务实例也序列化进响应。当前响应均为 dataclass/`AjaxResult`/`TableDataInfo`/dict/list，未触发 |
| 仅支持 JSON body，不支持表单 body | `app/routes/registry.py:213-230` | 低 | 当前 6 个 POST 中 3 个是 JSON body、3 个无 body；无 `application/x-www-form-urlencoded` 用法 |

### 3.5 异常与错误体契约

- **正确**：未捕获异常 → 500 + Spring 错误体；`log.exception` 打全栈；绑定/缺参→400；媒体类型→415；404 → Spring 形状。
- **问题 1（fail-open）**：`app/main.py:60-76` 在 Mapper 安装失败时 `return "failed: ..."` 继续启动；`app/main.py:86-93` 调度器启动失败也只记 `failed`。`app/routes/registry.py:341-377` 对无法导入/无法实例化的 Controller 只记 `unavailable` 并继续。Spring 的行为是**启动失败**。【静态】
- **问题 2（错误信息过于贫乏）**：所有业务异常都折叠成 `{"status":500,"message":""}`。Java 侧确实没有 `@ControllerAdvice`，但生产排障只能靠日志；建议在错误体中加 `traceId`（不改变现有字段，向后兼容）。
- **问题 3**：`RuntimeError("Invalid bound statement")` 在 HTTP 面表现为 500，符合 Java；但它发生在**请求时**而非启动时，意味着 4 个接口长期“带病上线”。

### 3.6 并发与线程池

| 项 | 现状 | 风险 |
|---|---|---|
| Web 并发 | FastAPI 同步 handler 跑在 anyio 线程池，**默认 40 个令牌**（实测） | 相比 Tomcat 默认 200，容量约为 1/5；`app/routes/registry.py:44-48` 文档提到的 `app.server.worker-threads` **并未实现**（全工程无此配置读取） |
| 进程模型 | `run.py` 单进程 uvicorn，无 `workers` 参数 | 无法横向扩展；一旦 `workers>1`，Redis/ES/调度器/导出任务表全部按进程分裂 |
| 共享内存状态 | Redis dict、ES 类级 dict、导出任务 `ConcurrentHashMap` | Redis/ES 替身**无锁**；并发请求下 `increment` 丢更新、`rightPop` 有 check-then-pop 竞态 |
| 调度线程 | 每个 `@Scheduled` 方法一个 loop 线程 | 实际线程数 = 任务数（10），而非 `ScheduledTaskRegistrar` 的 poolSize=10；语义接近但不可控 |
| 业务线程池 | `DataReliabilityService` 4 + 2；`KafkaProducerService` 1；`SnapshotFlowSyncService` 2；导出 2~4 | **大量线程池只在构造时创建**；若未来同时从多处 `new`，会重复建池、重复状态（`KafkaProducerService.py:126-133` 就递归 new 了 3 个服务） |
| 1 小时睡眠占用线程 | `DataReliabilityService.py:736-750`：每条消息提交一个 `Thread.sleep(3600000)` 清理任务到 4 线程池 | 第 5 条消息起清理任务排队 1 小时；这是 Java 原缺陷，但生产上会直接“卡死”清理/重试 |
| 导出背压 | `ThreadPoolExecutor(2,4,queue=200,CallerRunsPolicy)` | 队列满时 HTTP 请求线程执行整段导出，请求可能阻塞数分钟；Java 同缺陷 |

### 3.7 配置、日志、密钥

**配置**

- 优先级实现正确：环境变量（松弛绑定）> `application.yml` > 占位符默认值。

### 3.8 测试与门禁的真实有效性

**事实**

- `pytest`：**83 passed**，全部来自 5 个 `test_phase2*.py`。
- 66 个测试函数分布：路由/绑定 19、XML 引擎 11、ES 聚合 7、调度/cron 19、健康/序列化 10（合计 66）。
- **0 个业务 Service 单元测试**；业务断言在根目录 `_smoke_t08/t09*.py`（23 个脚本），pytest 的 `testpaths=["tests"]` 不会收集它们。
- 无 `pytest-cov`（dev 依赖也没有），**覆盖率无法量化**。
- 无 ruff/mypy/pyright，无 CI 配置。

> **回答“82 个用例是否只覆盖 happy path”**：**不是**。基建层包含失败路径断言：400/415/500 错误体、必填参数缺失、类型转换失败、`<foreach>` 空集合抛错、非法 cron 表达式、调度任务异常后继续、shutdown 幂等。真正的问题不是“路径类型”，而是“覆盖对象”——83 个用例全部集中在框架/替身层，**业务 Service 的成功路径都没有断言**，且没有任何用例执行真实 SQL。

**关键的“测试有效性”问题**

1. `tools/smoke_all_routes.py` 明确**不启动 lifespan**（不使用 `TestClient` 上下文），因此 `install_mappers()` 不执行，所有 Mapper 走内存实现。它证明的是“handler 可被调用”，**不证明 SQL 正确、也不证明真实数据正确**。
2. `tools/smoke_all_routes.py` 当前 **exit 1**：导出任务因 `index_not_found_exception` 变成 `FAILED`，三条 payload 断言失败。一个“门禁”长期红着，就失去门禁意义。
3. `tests/test_phase2c.py:310-312` 的断言是：

   ```python
   assert {name.rsplit(".", 1)[-1] for name in report.unavailable} <= {
       "LargeScaleQueryController", "ProgressiveQueryController", "UnifiedQueryController",
   }
   ```

   这是“允许集合”，`unavailable == []` 时也恒真。它**无法发现任何 Controller 掉线**。
4. `tools/check_parity.py` 只比较**方法名字符串**，不比较签名/语义；`OdsLwzxsfsjFeeRecords01Mapper.py` 中“推测 SQL”的实现也能通过 parity（随后运行时被替换成抛异常）。
5. `tools/check_parity.py` 扫描根是 `PROJECT_ROOT.parent`（整个 `car-monit-api`），一共扫到 **222** 个 `.java`（219 个业务源文件 + 3 个兄弟工程 `car-monit-api-rust/.run/*.java`），把后者算进 Tier B，**默认永久 exit 1**。

## 4. 技术栈对比

### 4.1 逐项对比

| 维度 | 当前实现 | Python 生产主流 | 当前优势 | 当前代价 / 风险 | 判定 |
|---|---|---|---|---|---|
| Web 框架 | FastAPI + Starlette，自定义 `DispatcherServlet` 复刻 | FastAPI `APIRouter` + Pydantic；Flask Blueprint；Django DRF | 保留 Spring 路由优先级、参数绑定、错误体；启动快 | 路由是生成表；handler 全同步；无请求校验模型；OpenAPI 只有壳 | **保留 FastAPI（资产）**；路由生成器保留为“漂移检测”，不建议继续作为运行时唯一真相 |
| 路由 | `app/routes/generated.py` 数据表 + 运行时解析 | 装饰器显式声明 | 与 Java 注解一一对应，可批量生成 | 表是构建产物，需手工重生成；无 drift 测试；不可读性差 | **必须付的代价**（1:1 约束下），但应加“重生成后 diff 必须为空”的门禁 |
| SQL / ORM | 原样 MyBatis XML + 自写解释器 + SQLAlchemy Core `text()` | SQLAlchemy ORM + Repository；Alembic；asyncpg | 复用 54 条真实 SQL，查询语义不重写 | 无编译期校验；每请求重新渲染；无 session/事务；结果映射靠反射 | **必须付的代价**（保留 XML 是最大资产）；事务/连接层可以现代化 |
| Schema 迁移 | 无（表由外部 GaussDB 维护） | Alembic（若拥有 schema） | 无重复建模 | 无 schema 契约测试 | **纯负担**（本项目不需要 Alembic），但建议加“表/列存在性”契约测试 |
| 校验 / 序列化 | 自写 Spring 绑定 + 自写 Jackson 序列化 | Pydantic v2 + 自定义 encoder；`orjson` | 字段名/日期格式/错误体逐字节对齐 | `BigDecimal→float`；无入参校验；维护成本高 | **必须付的代价**（为 1:1），但数字类型必须改 `Decimal` |
| DI / 生命周期 | 无容器；构造参数默认 `new`；`@PostConstruct` 手动调用 | FastAPI `Depends`；`dependency-injector`；`punq` | 无框架魔法，易读 | 单例语义丢失；漏启动 Bean；重复线程池 | **纯负担** → 用轻量单例注册表 |
| 配置 | 自写 YAML 子集 + `Environment` | `pydantic-settings` + PyYAML；`python-dotenv` | 与 Spring 优先级一致 | 子集解析；死配置项；双入口 | **纯负担**（解析器），**资产**（优先级语义） |
| 调度 | 自写 `CronExpression` + `ThreadPoolTaskScheduler` | APScheduler；Celery beat；K8s CronJob | cron 语义高保真、10 任务已对齐 | 无持久化、无分布式锁、无 misfire 策略 | **必须付的代价**（对齐 Spring cron）；多实例需补 leader 选举 |
| HTTP 客户端 | Forest 假实现 | `httpx` / `aiohttp` + 重试 | 离线可跑 | 外部系统从未被调用 | **纯负担** → 替换 |
| 消息队列 | Kafka/Pulsar/RocketMQ 假实现 | `confluent-kafka` / `pulsar-client` / `aio-pika` / Celery | 消费者代码可离线执行 | 写入不落地；可靠性代码建立在假成功之上 | **纯负担** → 必须替换 |
| 缓存 | 内存 dict + RESP2 只读 | `redis-py`（连接池、序列化器、集群） | 无外部依赖即可跑测试 | 不共享、无锁、TTL 不完整 | **纯负担** → 生产替换；测试保留 |
| 搜索 | 内存 ES + 客户端过滤 | `elasticsearch-py` 8.x + 真实 DSL | 离线演示 | 真实数据量不可用；导出/统一查询失效 | **纯负担** → 必须替换并翻译 DSL |
| 测试 | pytest 83 用例（基础设施层）+ 根目录冒烟脚本 | pytest + `pytest-cov` + `testcontainers` + `respx` | 框架层覆盖扎实 | 业务 0 单测；无覆盖率；无集成测试 | **资产（pytest 基建）**，需补业务/集成/覆盖率 |
| Lint / 类型 | 无 | ruff + mypy/pyright | — | 28k 行无静态检查 | **纯负担** → 立即加 |
| 打包 | `requirements.txt` 宽范围、无 lock | `uv` / `poetry` + lock；wheel/镜像 | 简单 | 不可复现；干净环境装依赖会与 `check_env` 冲突 | **纯负担** → 加 lock |
| 部署 | `python run.py` | Docker + gunicorn/uvicorn workers + K8s/systemd | 一条命令 | 无镜像、无健康分级、无优雅停机 | **纯负担** → 必须补 |
| 观测 | 文件日志 + 自造 `/health` | structlog/JSON + Prometheus + OpenTelemetry + Sentry | `/health` 可看依赖 | 无 metrics/trace/request log；health 永远 200 | **纯负担** → 必须补 |
| 密钥 | 明文 yml | env / Vault / K8s Secret | 与 Java 共用配置 | 口令入库 | **纯负担** → 外置 |

### 4.2 三类结论（这是本报告最重要的一节之一）

**A. 为了“一比一”必须付的代价（应保留）**

1. **MyBatis XML 解释器**：54 条真实 SQL 是这套系统最贵的资产。改 ORM 等于重写查询语义，必然引入偏差。
2. **Spring MVC 语义层**：路由优先级、`@RequestParam` 必填/默认值、`Map` 参数、`@ModelAttribute`、错误体、`AjaxResult` null 语义。这些是“接口契约”，不能交给 Pydantic 默认行为。
3. **Jackson 字段名/日期/字段顺序复刻**：`gantryCaptureBO` 这类名字无法从 snake_case 反推，必须有 `java_meta` 元数据。
4. **PageHelper 分页与 cron 语义**：分页的 count/limit/reasonable 与 cron 的六段式是行为契约。
5. **`application.yml` 原文 + 环境变量优先级**：保持“同一份配置”。

**B. 纯负担（应在生产版本中移除或隔离）**

1. Kafka/Pulsar/RocketMQ/ES/JdbcTemplate/Forest/Flink 的“假成功”替身。它们不会让系统更安全，只会掩盖故障。
2. 自写 YAML 子集解析器（应换 PyYAML/pydantic-settings，保持 key 语义即可）。
3. 无容器的“默认 new”依赖注入方式导致的重复实例与漏启动（用轻量单例即可解决，不需要引入完整 DI 框架）。
4. 根目录 45 个 `_*` 临时文件、23.2MB 日志、`_impl_*.txt` 等构建过程垃圾。
5. 自造 `/health` 作为唯一健康检查（应改为 liveness/readiness 两级，并把 DB/Redis/ES/MQ 分开）。

**C. 应该保留的资产**

1. **生成器 + 校验器组合**：`gen_routes.py` / `gen_java_meta.py` + `check_routes.py` / `check_mappers.py` / `check_parity.py` 是防漂移的核心机制，只是当前实现有范围/断言缺陷（修即可）。
2. **XML 原文 + `application.yml` 原文**：唯一真相，不应复制到 Python 树里再维护一份；应改为发布时打包。
3. **CronExpression / JavaBean / PageHelper / BigDecimal / 错误体** 这些高保真小模块：测试价值高，改造成本低。
4. **pytest 基建测试**（phase2a–2e）：覆盖了最容易出错的框架语义，应保留并扩展。
5. **`app/db/` 解释器设计**（Statement/Node/ParamObject/ResultMap 分层）：结构清晰，可继续演进。

## 5. 生产化优化建议（按优先级）

> 每条格式：**问题 → 影响 → 改法 → 代价 → 是否破坏“与 Java 行为等价”**。

### P0：阻断上线（必须先做）

#### P0-1 把 Mapper XML 纳入 Python 发布物，并在启动时校验数量

- **问题**：`app/db/registry.py:44-55` 的 classpath 根指向 `../pro-business-api`；Python 树内 XML 数为 0。
- **影响**：只部署 Python 目录 → 22 个 XML / 54 条 statement 丢失；Mapper 方法退回“移植期臆造实现”（静默错误数据）或抛异常；启动只打印 `0 mapper XML`，不失败。
- **改法**：把 `**/xml/*Mapper.xml` 复制到 `pro-business-api/src/main/resources/...` 或独立 `resources/mappers/` 并纳入打包；`install()` 后校验 `len(mapper_xmls) == 22` 且 `len(statements) == 54`，不等则**启动失败**（可用 `CAR_MONIT_ALLOW_MAPPER_GAP=true` 显式豁免）。
- **代价**：一个构建步骤 + 一份 142KB 资源；几乎无风险。
- **等价性**：**不破坏**。加载路径变化不影响 SQL 文本。

#### P0-2 中间件：真实客户端 or 明确“演示模式”

- **问题**：Kafka/Pulsar/ES/Redis/JdbcTemplate/Forest 全为进程内假实现。
- **影响**：生产上“发送成功”的消息不会到达 broker；ES 导出恒失败；外部接口从未被调用；多实例缓存不一致。
- **改法**（分两步）：
  1. **隔离**：把 `com/ java/ javax/ org/` 移到 `shims/`，用环境变量 `CAR_MONIT_RUNTIME=prod|shim` 控制 import；生产模式禁止 shim（启动自检直接报错）。
  2. **替换**：新增 `adapters/`（`RedisAdapter`、`EsAdapter`、`KafkaAdapter`、`PulsarAdapter`、`HttpAdapter`），业务代码依赖接口而非 `org.*` 类；ES 需要把 `QueryBuilder` 翻译为真实 DSL，`scroll` 用真实 search_after/scroll API。
- **代价**：中高（ES DSL 翻译是主要工作量）；需要真实集群联调。
- **等价性**：**不破坏业务语义**，但会改变“离线可跑”的开发体验（shim 保留给测试）。

#### P0-3 补 Spring Bean 生命周期

- **问题**：`SnapshotFlowSyncService` / `KafkaProducerService` 的 `@PostConstruct` 从未执行。
- **影响**：Java 启动即跑的“历史 300G 全量同步 + 增量同步 + Kafka 失败重试”在 Python 中不存在；数据链路缺失。
- **改法**：新增 `app/beans.py` 轻量单例注册表；启动时按 Java `@Service` 清单构造 Bean 并调用 `init()`；对 `SnapshotFlowSyncService.fullSync/incrementalSync` 加显式开关（默认关闭，避免一上线就全表扫库 + 打爆 Kafka）。
- **代价**：低（一个注册表 + 一份清单）；但**默认开启会立即产生真实负载**，必须由运维确认。
- **等价性**：更接近 Java；`fullSync` 默认关闭属于“有意的运维差异”，需在配置中写明。

#### P0-4 事务边界

- **问题**：`Database.execute` 每条语句独立 `engine.begin()`；无 session/UnitOfWork。
- **影响**：当前 HTTP 面无写操作，故**即时风险低**；但 `DataProcessService`（唯一 `@Transactional`）一旦启用，Java 的“MySQL 成功、ES 失败则回滚”无法复现。
- **改法**：引入 `unit_of_work()`（SQLAlchemy `Session` 或 `engine.begin()` 上下文），按 Java `@Transactional` 方法边界包住多条语句；对跨 ES/Kafka 的补偿用 outbox/重试表而非数据库事务。
- **代价**：中；需要梳理唯一的事务方法。
- **等价性**：**修复 Java 语义**（当前不可达，故不影响现有接口）。

#### P0-5 启动 fail-fast

- **问题**：Controller 不可用、Mapper 安装失败、statement 缺失均只记日志。
- **影响**：带着残缺路由/映射长期运行；监控看不到，直到用户报错。
- **改法**：`RouteInstallReport.ok` / `InstallReport.ok` 为 false → `raise` 并退出；已知的 6 个缺失 statement 放入**显式白名单**（并记录 TODO/工单号），白名单外任何缺失都失败。
- **代价**：低；需要维护白名单。
- **等价性**：与 Spring 启动失败语义一致。

#### P0-6 密钥与暴露面

- **问题**：yml 明文口令；`/docs`、`/openapi.json`、`/health` 无鉴权；`/health` 输出 DB/Redis/ES 地址。
- **影响**：凭据泄露；攻击面扩大；健康信息被探测。
- **改法**：生产用环境变量/Secret 注入并移除 yml 明文；`/docs`、`/openapi.json` 仅非生产开启；`/health` 拆 `liveness`（200 仅表示进程活）与 `readiness`（DB/Redis/ES 探针），生产只暴露内网。
- **代价**：低。
- **等价性**：**不破坏**（这些端点本就是 Python 新增，非 Java 契约）。

### P1：高优先级（决定能否稳定运行）

#### P1-1 数字类型：`BigDecimal` → `Decimal`

- **问题**：`BigDecimal` → `float` 影响 7 个 domain 文件、39 个字段；序列化再 `float()`。
- **影响**：金额/重量/尺寸的十进制文本与 Java 不一致（`1.50` vs `1.5`；大数科学计数）；下游对账/导出可能出现差异。
- **改法**：domain 字段改 `Decimal`；`map_row` 的 `coerce_value` 支持 `Decimal`；`to_jsonable` 用 `orjson` 的 `Decimal` 支持或输出原始数字字符串（需确认 Jackson 的 `BigDecimal` 文本行为）。
- **代价**：中（7 个实体 + 快照测试）。
- **等价性**：**修复偏差**，更贴近 Java。

#### P1-2 并发模型与部署形态

- **问题**：单进程、40 线程；`app.server.worker-threads` 文档存在但未实现；多 worker 会分裂所有内存状态。
- **影响**：吞吐约为 Java 的 1/5；无法水平扩展。
- **改法**：短期（保持 shim）：单 worker + 可配置 anyio limiter（实现 `app.server.worker-threads`）；中期（替换中间件后）：`uvicorn --workers N` 或 gunicorn + 共享 Redis/ES/DB；调度器加分布式锁（Redis `SET NX` 或 K8s CronJob）。
- **代价**：中；需要压测基线。
- **等价性**：单请求语义不变；多实例下调度去重是**新增运维语义**，需确认。

#### P1-3 可观测性

- **问题**：无 metrics、无 traceId、无访问日志；health 只探 DB；日志是本地文件。
- **影响**：故障只能靠翻日志；无法定位慢请求、导出积压、ES 降级频率。
- **改法**：`structlog`/JSON 日志 + `X-Request-Id` 中间件；Prometheus 指标（QPS、P95、DB 池等待、导出队列、fallback 次数）；`/metrics` 内网暴露；错误日志带 traceId；访问日志开启（当前 `logging_config.py:61` 禁用）。
- **代价**：中。
- **等价性**：**不破坏**响应体（仅新增响应头/日志）。

#### P1-4 CI 与门禁修复

- **问题**：`check_parity` 永久红；`smoke_all_routes` 红；`check_env` 依赖未声明包；无 CI。
- **影响**：没人再信任门禁；回归靠肉眼。
- **改法**：
  - `check_parity` 扫描根改为 `PROJECT_ROOT`（只看 Python 树 + 两个模块），排除兄弟工程；
  - `smoke_all_routes` 对 ES 导出用例改为“允许 FAILED 但断言错误类型”，或先建内存索引；
  - `check_env` 只检查 `requirements.txt` 声明的包；声明 `redis/elasticsearch/APScheduler/PyYAML` 为 dev 依赖或直接删除检查；
  - CI 串行跑：`ruff` → `mypy` → `pytest` → `check_routes` → `check_mappers` → `check_parity` → `smoke_all_routes`；
  - 新增 `gen_routes`/`gen_java_meta` **重生成 diff 必须为空** 的 job。
- **代价**：低到中（一次性配置）。
- **等价性**：不破坏业务。

#### P1-5 业务测试与集成测试

- **问题**：0 个业务 Service 单测；`_smoke_*.py` 未进 pytest；无覆盖率。
- **影响**：166 个业务文件的逻辑回归无保护；重构风险极高。
- **改法**：把 `_smoke_t08/t09*.py` 的断言迁入 `tests/business/`（用 pytest 参数化）；新增“真实 DB 集成测试”（可标记 `@pytest.mark.integration`，CI 用 GaussDB service container）；新增“SQL 快照测试”（对 54 条 statement 渲染结果做 golden file）；加 `pytest-cov`，先设 60% 门槛再逐步提高。
- **代价**：中高（迁移 23 个脚本 + 建测试库）。
- **等价性**：不破坏。

#### P1-6 配置收敛

- **问题**：`app/settings.py` 有 8 个属性无调用点；业务侧各自 `Environment().value(...)`；`CAR_MONIT_PORT` 与 `server.port` 不一致。
- **影响**：配置改动可能“改了不生效”；健康信息误导。
- **改法**：只保留一个配置入口（`Environment`），`settings` 改为薄缓存且每个属性都有消费点；`server_port` 优先读 `CAR_MONIT_PORT`；新增“配置项引用扫描”脚本（grep `@Value` 字符串 ↔ 实际调用）。
- **代价**：低。
- **等价性**：不破坏。

#### P1-7 fee 接口：补 XML 还是保留缺陷

- **问题**：`/base/feerecords/list`、`/base/feerecords/listToExport`、`/base/feerecords/{bigId}`、`/progressive/trailfitting/list` 因缺少 XML statement 恒 500（共 4 个；Java 侧同样缺）。`selectGantryNum`、`selectOdsLwzxsfsjFeeRecords01ListNew`、`selectZdataTrailFittingById` 无 HTTP 调用方。
- **影响**：接口不可用；若业务实际依赖，则迁移“完成”是假象。
- **改法**：与业务确认这 6 个方法的真实 SQL（从生产库执行计划/历史 SQL 日志/上游 DBA 获取）；补 XML 后删除 Python 猜测实现与白名单。
- **代价**：中（需要业务/DBA 输入）。
- **等价性**：**会改变 Java 缺陷行为**（从 500 变为可用），必须业务签字。

#### P1-8 依赖、打包与部署

- **问题**：`requirements.txt` / `pyproject.toml` 只有宽范围（`fastapi>=0.115,<1.0`、`SQLAlchemy>=2.0.30,<2.1`），无 lock；`check_env.py` 检查 `redis/elasticsearch/APScheduler/PyYAML`，但 `requirements.txt` 明确不声明它们；无 Dockerfile、无进程管理配置。
- **影响**：干净环境 `pip install -r requirements.txt` 后 `check_env` 必红；两台机器可能装出不同版本；生产启动方式未定义。
- **改法**：用 `uv lock` 生成锁文件并从锁文件导出 `requirements.txt`；`check_env` 与声明对齐（把 4 个包列为 dev 或删除检查）；提供多阶段 Dockerfile（非 root、只读 rootfs、`/health` 作为 liveness），并明确单 worker/多 worker 的启动参数。
- **代价**：低到中（一次性）。
- **等价性**：不破坏。

### P2：中优先级（生产稳定后）

#### P2-1 替身层目录化与 import 守卫

- 把 172 个替身文件移到 `shims/`，并在 `bootstrap` 中按运行模式注册；生产启动检测 `sys.modules` 中是否加载了 `org.elasticsearch.*` 等 shim，命中即失败。
- **代价**：中；**等价性**：不破坏。

#### P2-2 Redis 语义补全

- 列表/哈希/集合 TTL；`setIfAbsent/increment/rightPop` 加锁或改用 `threading.RLock`；如果接真实 Redis，写操作也要穿透（注意 Java FastJson `@type` 兼容，建议统一改为 JSON 字符串协议）。
- **代价**：中；**等价性**：修复并发缺陷。

#### P2-3 ES 查询与导出

- `QueryBuilder.matches` 客户端过滤 → 真实 DSL；scroll 生命周期；索引/别名/ILM 初始化走真实 API；导出失败的错误分类（索引不存在 vs 集群不可用）。
- **代价**：高；**等价性**：查询结果集需与内存实现逐条对比（建议 golden test）。

#### P2-4 SQL 性能护栏

- 禁止 `selectList(<predicate>)` / `selectCount(<predicate>)`（抛 `NotSupported`，强制改写为 Wrapper/XML）；给 `LIMIT 1000` 兜底路径加监控；评估 `orderBy` 注入正则与真实 SQL 的交互。
- **代价**：低；**等价性**：若现有路径依赖全表扫描，行为会变为报错（更安全）。

#### P2-5 线程池治理

- `DataReliabilityService` 的 1 小时 `Thread.sleep` → `ScheduledExecutorService.schedule(1h)`（不占工作线程）；线程池改有界队列 + 明确拒绝策略；应用关闭时统一 `shutdown`（当前 `UnifiedExportService.destroy` 与 `cleanExpiredTasks` 均无调用方）；导出 `CallerRunsPolicy` 改为拒绝 + 客户端轮询。
- **代价**：中；**等价性**：修复 Java 原缺陷（需业务接受）。

#### P2-6 日志与仓库卫生

- 删除根目录 `_smoke_*.py`（迁移到 `tests/business/`）、`_impl_*.txt`、`_domain_spec.txt`、`py.log`；日志改 stdout（容器采集）+ 本地仅 debug；日志滚动改按天。
- **代价**：低；**等价性**：不破坏。
