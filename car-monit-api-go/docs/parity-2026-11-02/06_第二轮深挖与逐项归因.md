# 06 第二轮深挖：剩余不一致的逐项归因

范围：`05` 修复后仍非 OK 的 71 条（DIFF 24 / STATUS 25 / NONDET 22）逐条打穿。
做法上加了三件事：**先修工具再修结论**、**用数据库真值做第三方校准**、**用 Java 日志做根因取证**。

## 1. 先纠正工具：22 条 NONDET 全是我的假差异

`feeGantry` 与 `snapshotflow` 的 22 条 NONDET，重看代码才发现两端在 Controller 里
`rtn.setId(StringUtils.getUUID())` —— **每次响应都重新生成行 id**
（`OdsRtSzdnSnapshotFlowAddcodeController.java:79,127`、`OdsLwzxsfsjFeeGantryFusion01Controller.java:38`）。
我的工具拿这个随机字段当主键对齐、又参与字段比对，于是"每一行都不一致"。

| 修正 | 依据 |
|---|---|
| `snapshotflow` 改用 `datauuid` 对齐 | 同一行两端 `datauuid` 完全相同（`c2d437fd-5c2e-40b5-98fd-6581a0f94c1b`） |
| 这两张表把 `id` 列入用例级豁免 | Java 自身两次请求的 `id` 就不同（NONDET 自校验早已提示，但我当时误读成"数据在变"） |
| 无主键的表（`vehicleweight`，uuid 列全 null）改用**整行多重集**比对 | 之前按 `uuid=null` 对齐把所有行塌成一条 |

修完：NONDET 22 → **0**，`OK` 从 310 起步继续上升。

### 顺手发现并修掉一个真的 Go 缺陷（P-ID-1）

`StringUtils.getUUID()` 是 `UUID.randomUUID().toString().replaceAll("-","")` → **32 位无横线**；
Go 用 `uuid.NewString()` → **36 位带横线**。两端格式不同（长度和字符集都不同）。
已在 `internal/utils/uuidutil.go` 新增 `GetUUID()` 并替换 3 处调用（含把 `multisource.go`
里重复的私有 `stripDashes` 合并掉）。

> 注意 `export.go` / `large.go` 的 `taskId` **保持带横线**，因为实测 Java 的 taskId 就是标准 UUID
> （`7441f716-bdfa-4e2c-9203-…`），不能一刀切。已在函数注释里写明这条边界。

## 3. 查询族 5 条 DIFF：Java 的降级路径根本跑不通（Go 是对的）

`/api/v1/large/fee|trail`、`/api/v1/unified/fee|trail/list` 全是 **Java 0 行、Go 5 行**。
逐层查证后定位到一句 SQL 错误：

```

  ERROR UnifiedQueryService:134 - [统一查询] 查询失败 ds=FEE, useEs=true
```

| 事实 | 证据 |

| 降级后 Java 仍失败 | `OdsLwzxsfsjFeeRecords01.java:25` 是 `@TableName("ods_lwzxsfsj_fee_records_01")`——**没有 schema**；而 `psql` 实测 `search_path="$user",public`，`public.ods_lwzxsfsj_fee_records_01` 不存在，表在 `jl_data01` |

| 库里确实有该窗口数据 | `select count(*) … where transtime between '2025-10-01' and '2025-10-02'` → **200 行**（全表 1016 行） |

**判定**：这 5 条是 **Java 缺陷 + Go 已正确修复**。切换后表现为"Java 一直返回空、Go 返回真实数据"，
属可见的行为改进，但要让业务方确认（他们可能已经按"永远为空"写了兜底逻辑）。

## 4. 时区：我一度判错，用数据库真值纠偏

Go 的 `/large/fee` 返回 `transtime=2025-09-30 18:18:39` 而请求窗口是 10 月 1 日，
我据此判定"Go 的时间过滤失效"。校准后发现**完全相反**：

| 来源 | 值 |
|---|---|
| 数据库真值 | `2025-10-01 00:09:04` |
| Java `:9902` | `2025-09-30T16:09:04.000+00:00` |
| Go `:9903` | `2025-09-30T16:09:04.000+00:00` |

**Java 也做 UTC 偏移**，两端逐字符一致。原因在 `model/datetime.go`：Go 与 Java 都是"按 UTC 格式化"，
而 `snapshottimeStr` 这类本地串两端也都相同（`2025-11-16 15:14:17`）。
教训：只比两端会得出"两边都错"的错误结论，**必须引入第三方（数据库真值）**才能判定方向。

## 5. 日期参数绑定：实测矩阵驱动的一处行为重写

`bind_test.go` 里用 `TestParseParamDateMatchesJava`（9 拒绝 + 5 接受）和

## 6. `carTrackQueryByTime` 的点数差异：不是去重，是我加的 ORDER BY

上一轮记为 P-TRK-2「去重逻辑不一致」。深挖后**归因错了**，真正原因是选行不同：

```
车牌 赣AU6P90 在 jl_data01.zdata_trail_fitting 里有 2 条记录：
  cid=39259e80… entime=2025-10-01 19:48:55   ← Java 取到这条
  cid=0a1736ee… entime=2025-10-02 17:32:42   ← Go 取到这条
Java 的 getHistoryTrail 没有 ORDER BY；Go 自己补了 Order("cid, extime")，
而 '0' < '3'，于是同一车牌换了一条轨迹记录 → 整串 trailList/轨迹点都不一样。
```

两端输入的 `trailPoints` 原始串本身就不同（已验证 `!=`），所以差异在**取数层**而非富集层。

修复：去掉 `GetHistoryTrail` 里 Go 自补的 ORDER BY（`internal/repo/zdata_trail_tracks.go`），
代价与 Java 相同 —— 无 ORDER BY 的分页不保证翻页稳定。同时修正
`carNo` / `carNoList` 的关系：Java 的 XML:140 与 XML:151 是**两个独立 `<if>`（AND）**，
Go 之前写成 `if / else if`，等于"有 carNoList 就忽略 carNo"，调用方同时传两者时结果会偏大。

> 去重逻辑经逐行对照（`SysUtilServiceImpl.java:2092-2150` vs `service/sysutil.go:249-307`）
> **是一致的**：合并键 `stateType+locationCode`、窗口 4 分钟、`Math.abs` 差值、
> 只有 GantryCapture/StationCapture 入表、图片累加方式全部对齐。
> Java 那段按时间排序的代码确实被注释掉了（`:2096-2100`），Go 也没排。

## 7. 更大的发现：历史轨迹查询**少投影 15 列**（P-TRK-3，BLOCK）

把 ORDER BY 去掉、行能对齐之后重测，发现 `tracks` 对象仍有大量字段是 null。
逐字段统计：**94 个车牌共 2162 个字段值 Java 有、Go 为 null**，例如
`tracks.enaxlecount=2`、`tracks.entollstationname="江西宁都北站"`、`tracks.exweight`、
`tracks.startLonDec`、`tracks.exvehicleid` …

根因在投影，不在序列化：

| 事实 | 证据 |
|---|---|
| Java 的 `getHistoryTrail` 投影 **20 列** | `ZdataTrailTracksMapper.xml:116-136` |
| Go 只投影 **5 列** | `historyTrailColumns` 原值（uuid / plate_key / enter_time / exit_time / trail_points） |
| 旧注释的解释 | 「那 15 列在 Java 实体上是 `@TableField(exist=false)`，Go 对应 `gorm:"-"`，选了也回填不了；下游只读这 5 个」 |
| 但这个解释只覆盖内部使用，没覆盖**响应契约** | Java 照样把这 15 列输出到 `tracks` 里，调用方拿得到 |
| 不能直接删 `gorm:"-"` | 库里 `zdata_trail_fitting` 有 20 列，而 `zdata_trail_tracks` **只有 10 列**；这两个查询共用同一个模型，去掉 `gorm:"-"` 会让 `/base/trailtracks/list` 直接报"列不存在" |

**改法**：新增 `historyTrailRow` 投影结构体（这 15 列带真实 gorm column tag），
`GetHistoryTrail` 扫进它再 `toModel()` 逐字段拷回模型 —— CRUD 那条 SQL 完全不受影响。

修完实测（`carTrackQueryByTime`，pageSize=300，按车牌对齐后逐字段比）：

```
共同车牌 94；行内容完全一致 94；残余差异 {}
```

顺带修掉同函数里的一处条件缺失：Java 的 `bannian`/`yiyue` 分支是**双边**条件
（XML:144-150 `extime >= now() - 180 and extime <= now()`），Go 只有下界，
会把 `extime` 在未来的行多带出来。已补齐上界。

## 8. 契约类：本轮改了两处、留了一处待定

| 项 | 改动 | 实测 |
|---|---|---|
| P-ERR-3 请求体非法 | `jsonBody` 区分"无请求体（Java 给 null，200）"与"有体但解析不了（Java 400）"，后者走 `BindError`；`changeTrailInfo` 同理由 `BizError(400)` 改为 `BindError(400)` | 非法 JSON 体、空体：Java 400 / Go **400** ✅ |
| P-ERR-4 结尾斜杠 | `RedirectTrailingSlash` 由 `false` 改 `true`（原注释"与 Spring 一致"判定反了：Java 配了 `ant_path_matcher`，斜杠是 200） | `GET /base/gantry/list/`：Java 200 / Go **301**，跟随重定向后 200 且数据与 Java 完全一致（`total=1526`）✅ |
| P-ERR-1 404/405 响应体 | **未改** | 见下节 |

### 为什么没顺手改 404/405 的响应体

Java 是 Spring 错误体 `{timestamp,status,error,message,path}`，Go 是 `{code,msg}`。
Go 的 `middleware.BindError.envelope` 已经能产出 Spring 那 5 个键（数字 id 转换失败就在用），
所以技术上可改；但 NoRoute/NoMethod 是**全局兜底**，一改就影响所有未匹配请求的既有消费方，
属于契约决策而非缺陷修复。建议连同 `P-SER-1` 一起由业务方拍：

| 决策项 | 选项 A（严格对齐 Java） | 选项 B（保留 Go 现状） |
|---|---|---|
| 404/405 响应体 | 全局换成 Spring 错误体 | 保留 `AjaxResult`，前端按 `code` 判 |
| 未捕获异常 | base 类 Controller 回 HTTP 500 | 统一 HTTP 200 + `code:500` |
| `TrailBo`/`TrailInfo` 的空串 | 输出 `null` | 输出 `""` |

## 9. `null` vs `""`：已量化，等拍板（P-SER-1）

实测取证：取 Java `carTrackQueryByTime` 的 **797 个真实轨迹点**逐字段扫描，
**没有任何字段出现空串 `""`** —— Java 只会输出 `null` 或有值。所以"空值⇒null"对这两个 DTO 是安全映射。

改动面已量出来：

| 位置 | 裸 `string` 字段数 |
|---|---|
| `model/trail_bo.go` | 27 |
| `model/trail_info.go`（trailUuid） | 1 |
| 其它 DTO（`CarVO`/`CarParaVO`/`SuspiciousCarVO`） | 11 |
| 代码侧读写点 | ≈106 处，集中在 `service/sysutil.go`(43) 与 `service/multisource.go`(33) |

好消息是这个改造**没有静默陷阱**：`utils.IsNull` 已经显式处理 `*string`（nil → `""`），
`model.Str()` / `model.Val()` 这套助手在本仓已经用于实体，编译器能兜住全部漏改的点。
两条可选路径：

- **A. 字段改 `*string`**：语义最正，106 处机械改动，编译期可验证；
- **B. 加 `model.Nstr` 命名类型 + 自定义 `MarshalJSON`（空则输出 null）**：调用点几乎不改，
  但要在写入处做 `model.Nstr(...)` 转换，且要防"实体侧误用"。

本轮**没有实施**：它是 D 类（结果不同）而非 B 类（数据丢失/接口坏），且属于序列化契约变更，
影响前端 `x != null` 判断。等你在 A / B / 保持现状之间选一个，我再动。
