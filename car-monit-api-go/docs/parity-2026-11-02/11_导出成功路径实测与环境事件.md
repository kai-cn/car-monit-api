# 11 导出成功路径实测 + 环境事件（第六轮）

三件事：① 恢复两端在线时发现环境已经坏了一大块；② 导出**成功路径第一次真正跑到**，
并拿到内容级证据（顺带更正一个说法：两端导出的都不是 xlsx，是 CSV）；
③ 把 `10` §5 留着的 P-QRY-1 时间格式问题定死——**建议不复刻**，依据见第 4 节。

## 1. 环境事件：磁盘打满 → ES 进入 flood stage → 三个服务一起没了

18:07 前后 Java `:9902`、Go `:9903`、ES `:9200` **同时消失**，不是某一次重启失败。
ES 自己的日志给了原因：

```
[2026-11-03T18:05:33][WARN][o.e.c.r.a.DiskThresholdMonitor] [node-1]
  flood stage disk watermark [95%] exceeded on [fqv3naVfTuaxhbnVrZCm...
```

当场核实：

| 盘 | 用量 | 剩余 |
|---|---|---|
| C: | **98%** | 5.6 GB |
| D:（项目 + ES data + GaussDB 虚拟机所在） | **92%** | 24 GB |

Java 的日志目录 `logs/` 单个项目就 **478 MB / 49 个文件**（10 MB 一切，滚到 `.42`）。

**遗留问题（还没修，等你拍板）**：三个索引至今仍带 flood stage 的后遗症标记——

```
snapshot_flow / fee_records / trail_fitting:  index.blocks.read_only_allow_delete = "true"
```

ES 在磁盘回落到水位之下后**不会自动清掉这个块**。影响面：
**任何 ES 写入现在都会失败**（同步类接口 `/api/v1/large/sync/*`、文档写入），
读取与 scroll 不受影响（所以本轮导出实测能做）。清除命令：

```bash
curl -XPUT "localhost:9200/_all/_settings" -H 'Content-Type: application/json' \
  -d '{"index.blocks.read_only_allow_delete": null}'
```

我没有执行：磁盘还在 92%/98%，清了锁之后 ES 可能直接写爆，**先腾空间再清锁**才对。

服务现已恢复：Java 10460（`-Xmx2048m -Dserver.port=9902 -jar target/pro-business-api-1.0.jar`，
**不带**任何临时参数）、Go 20920（`configs/config.verify.yaml`）。
恢复后抽检：`gantry/list` 两端 total=1526/rows=5、`carTrackQueryByTime` 两端 total=112/rows=5，一致。

## 2. 先更正一个说法：导出的不是 xlsx，是 CSV

`LargeScaleQueryService.java:392` 与 `internal/service/large.go:387` 写的都是

```
export_<type>_<taskId>_p<N>.csv
```

表头 `datauuid,platenumber,snapshottime,detail`，`detail` 列是整行 JSON。
两端命名与列结构**同构**。此前文档里"导出成功路径"的表述没错，但"xlsx"这个预期是错的。

## 3. 成功路径怎么跑通的

导出**恒走 ES scroll**（`executeExportScroll`，`:326`），而现网索引的时间列是 `text`
→ sort 必 `all shards failed` → 两端一律 FAILED。所以只要 mapping 不动，成功路径就碰不到。

做法：**新建一个副本索引并只改 mapping，不碰原索引**：

1. `PUT snapshot_flow_parity`：复制 `snapshot_flow` 的 36 个字段，
   只把 `snapshottime`/`transtime`/`extime`/`entime` 从 `text` 改成
   `date`（`format: yyyy-MM-dd HH:mm:ss||strict_date_optional_time||epoch_millis`，
   按实际取值 `2025-09-08 10:51:00` 选的）；副本 `replicas=0`（单节点，避免 yellow 干扰）。
2. `POST _reindex` 把 300 篇原文档搬过去（`created:300, failures:[]`）。
3. 两端**临时**指向它：Go 用一份改写 `elasticsearch.index.snapshot` 的临时配置；
   Java 用 `-Delasticsearch.index.snapshot=snapshot_flow_parity` 重启一次。
4. 实测（窗口 2025-09-08 00:00:00 ~ 09-09，数据全在 09-08 那天，300 篇）：

```
java: status=COMPLETED totalExported=300 filePartCount=1
go  : status=COMPLETED totalExported=300 filePartCount=1
```

`05`/`07` 里"导出成功路径在本环境无法实测"这句**已经不成立**，本轮跑通了。

两个环境层面的差异顺带记下来：Java 的 `optimization.export.dir=/data/export`
在 Windows 上落到 **`D:\data\export\`**（盘根，跟项目无关），Go 是 `./data/export`（已 gitignore）。

## 4. 内容级对比：Java 的 CSV 是坏的，Go 的是合法的

用标准 `csv` 解析器读回各自产物：

| | Java | Go |
|---|---|---|
| 文件 | `D:\data\export\export_snapshot_a8f1af36…_p1.csv` | `car-monit-api-go/data/export/750c12e2…_p1.csv` |
| 大小 | 331,830 B | 384,330 B |
| 行数 | 301 | 301 |
| 表头 | `datauuid,platenumber,snapshottime,detail` | 同 |
| **解析出的列数集合** | **{4, 39}** | **{4}** |
| detail 能否 JSON 解析 | **否**（`Expecting value: line 1 column 1`） | 是，37 键 |

根因在 `LargeScaleQueryService.java:406`：

```java
currentWriter.write(id + "," + plate + "," + time + ",\"" + detail + "\"\n");
```

`detail` 是 JSON，里面全是 `"`，而这里只是把整段用 `"` 包起来、**没有把内部的 `"` 翻倍**。
任何 RFC 4180 解析器都会在第一处内嵌引号处终止该字段 → 一行被拆成 39 列。
Go 用 `csv.Writer`，自动翻倍成 `""`，所以能正常读回。

另外两处次要差异：

- **Go 的 detail 多一个 `_id` 键**（37 vs 36）。来源是 `internal/es/client.go` 的
  `parseHits` 里 `src["_id"] = h.ID`；Java 用的是 `hit.getSourceAsMap()`，不含 `_id`。
- 键顺序不同（Go `encoding/json` 对 map 按字母序，Java fastjson 按源顺序），
  所以逐字节比对本来就不可能，只能逐字段比。

**建议**：

1. **CSV 引号——不要让 Go 复刻 Java。** Java 这里是明确的缺陷。但有个前提要先查：
   既然 Go 现在产出的是**合法 CSV**而 Java 是**不合法 CSV**，那说明**要么没人在消费这个文件，
   要么下游用的是宽容/手写解析器**。切到 Go 后列数会从"看起来 39 列"变成"规范 4 列"，
   手写的下游很可能直接错位。这条必须在灰度前用真实消费方验一次，不能想当然。
2. **`_id` 建议去掉**（一行），让差异只保留在有意的地方；留着也说得通（`_id` 对排查有用），听你的。

## 5. P-QRY-1 时间格式：建议**不复刻**（把 `10` §5 的待决项定死）

`10` §5 留的问题是：Java 对 `2025-10-01`（纯日期）和 `2025-10-01T00:00:00` 返回空集，
Go 能查出 5 条，要不要让 Go 也拒绝。

读完 Java 的调用链后，答案是**这不是一条策略，是一串两次失败的级联**：

| 步 | 代码 | 发生什么 |
|---|---|---|
| 1 | `shouldRouteToEs` `:183-192` | `parseToMillis("2025-10-01")` 走 `Timestamp.valueOf` 抛异常 → catch → `return true`，注释写"时间格式异常时保守走 ES（ES 对时间格式更宽容）" |
| 2 | `queryFromEs` `:245` | `.sort(timeField, DESC)` 打在 `text` 列上 → `all shards failed` → 抛出 |
| 3 | 外层 catch `:137-140` | 降级 `queryFromMysql` |
| 4 | `queryFromMysql` `:321` | `new Timestamp(parseToMillis(startTime))` **用同一个严格解析器，又抛一次** |
| 5 | 内层 catch `:142-143` | `return Collections.emptyList()` |

也就是说第 1 步"保守走 ES"的理由（ES 对格式更宽容）在第 2 步被它自己的 sort 否决了，
第 4 步又拿当初解析失败的同一个串再解析一遍。**净效果是对一个完全合法的输入静默返回空**。

所以：**不复刻**。Go 现在的行为（解析得动就查、查出真实数据）是对的；
r12 里那 3 条 DIFF 保持"已测量、不归因于 Go 缺陷"。真要消除差异，修法是修 Java
（`parseToMillis` 支持 `yyyy-MM-dd`、或降级前把时间归一化），而不是把 Go 一起弄坏。

## 6. 复现与清理

```bash
# 建副本索引 + reindex（只新增，不改原索引）
curl -XDELETE localhost:9200/snapshot_flow_parity
curl -XPUT localhost:9200/snapshot_flow_parity -H 'Content-Type: application/json' -d '{...36 字段，时间列改 date...}'
curl -XPOST 'localhost:9200/_reindex?refresh=true' -H 'Content-Type: application/json' \
  -d '{"source":{"index":"snapshot_flow","size":500},"dest":{"index":"snapshot_flow_parity"}}'

# Go：临时改 configs/config.verify.yaml 的 elasticsearch.index.snapshot（本轮用的是临时副本，已删）
# Java：java -Xmx2048m -Dserver.port=9902 -Delasticsearch.index.snapshot=snapshot_flow_parity -jar target/pro-business-api-1.0.jar

# 两端各提交一次（窗口要有数据：现网 snapshottime 全在 2025-09-08）
curl -XPOST 'localhost:9902/api/v1/large/export/submit?startTime=2025-09-08%2000:00:00&endTime=2025-09-09%2000:00:00'
curl -XPOST 'localhost:9903/api/v1/large/export/submit?startTime=2025-09-08%2000:00:00&endTime=2025-09-09%2000:00:00'
# 轮询 /api/v1/large/export/status/{taskId} 直到 COMPLETED

# 用完清理
curl -XDELETE localhost:9200/snapshot_flow_parity
```

> `snapshot_flow_parity` **本轮结束后仍保留在 ES 里**（删它之前先确认你不再复现）。
> 两端服务已恢复为不带任何覆盖参数的正常启动，原索引未被改动。
