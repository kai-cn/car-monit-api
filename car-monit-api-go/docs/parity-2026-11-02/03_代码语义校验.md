# 03 代码级语义校验

覆盖实测打不出来的部分：SQL 谓词、排序、序列化、Redis key 归属、定时任务、MQ、配置项。
四个方向由并行代码审阅产出，**每条都经过我复核**——证伪的写在第 7 节，未验证的明确标注。

## 1. 谓词覆盖（19 张表全量机械对照）

工具：`tools/predicates.py`，解析 Java mapper XML 的 `<if>` 与 Go repo 的 `tx.Where`，比对列名集合。

| 结果 | 表 |
|---|---|
| **完全一致（0 缺 0 多）** | sfsjcxx, sfzjcxx, fwqclls, feeStationEnter, feestationexit, snapshotflow, provcapture, stationcapture, gantry, gantryIp, vehicleweight, section, toll, org, feeGantry（Go 多 1 个 `params`） |
| **Go 缺实现** | ~~`trailtracks`（缺 6）~~ → **已由 P-FILT-1 补齐，现在 0 缺**；`fwqjcxx`（缺 28）、`feerecords`（Java 无 list 语句，Go 自造 13） |
| **Go 自行新增** | `tollStationIp` 多了 `id`、`trailtracks` 多了 `enter_locationcode/exit_locationcode/ervehicleid/extime` |

> 本表是**初测（full-asis）时**的快照。`trailtracks` 那 6 个缺失条件已在 `05` 修复，
> 第三轮复核重跑 `predicates.py` 后该表为 **0 缺 4 多**（多的是 Go 主动补的导出列）。
> 现在仍缺的 2 张都不是 Go 的问题：`fwqjcxx` 的 28 个引用的是 SELECT 别名（Java 自己写错，实测 500）、
> `feerecords` 的 XML 里根本没有 list 语句。

`trailtracks` 曾是**最明确的缺陷**（现已修复）：`internal/repo/zdata_trail_tracks.go:210-221` 的
`applyZdataTrailTracksFilters` 只做了 `uuid / enter_locationcode / exit_locationcode` 三个条件，
而 `ZdataTrailTracksMapper.xml:37-43` 定义了 7 个 —— **type、point_count、plate_key、enter_time、exit_time、trail_points 全丢**。
实测印证（改前）：`?type=0` 时 Java `total=879`、Go `total=1379`（等于没过滤）；
定稿两端均 `879`，见 `raw/trailtracks-filter-type.{java,go}.http`。

为什么 Go 会整片丢条件：`internal/handler/bind.go:57` `_ = setByString(...)` **忽略绑定错误**，
`setByString` 的 `default:` 分支对不认识的类型直接返回 error；
模型里 `Type *int`、`PointCount *int64` 能绑上，但 repo 侧压根没用它们拼 WHERE ——
所以根因分两层：**repo 少写条件**（主因）＋ **绑定失败静默**（让问题不可见）。

## 2. 排序

| | Java | Go | 影响 |
|---|---|---|---|
| `/list` 类 19 张表 | mapper XML **无 ORDER BY**（`snapshotflow` 的 `selectOdsRtSzdnSnapshotFlowAddcodeList` 亦无） | 仅 `snapshotflow` repo 加了 `Order("snapshottime desc")`（`:100`）、`trailtracks` 历史查询加 `Order("cid, extime")` | Go 的分页是「取 `offset+pageSize` 行再内存切」（`crud.go:173-178`），没有确定序就会漏行/重行，所以 Go 补排序是**必要的**；代价是首页内容与 Java 不逐行相同 |
| `orderByColumn/isAsc` | `PageUtils.java:23-25` 拼进 ORDER BY，`SqlUtil.java:31-42` 白名单不通过则抛 `UtilException`（→HTTP 500） | `bind.go:187` 明示"未实现" | 实测 13 张表行集不同（`02` D 类） |

**结论**：Java「无 ORDER BY + PageHelper 分页」本身是有缺陷的组合（翻页可能漏行），
Go 加确定序是修正方向，但必须让调用方知晓"同一页内容会变"。

## 3. 序列化

正向结论（跨 358 条用例统计）：**TYPE / NUMFMT / SHAPE 差异 0 处**。
即数字精度（Long 转字符串、BigDecimal 标度）、日期格式（`yyyy-MM-dd HH:mm:ss` vs RFC3339）、
空数组 vs null、信封结构，在两端都返回数据的场景下**完全一致**。
`javalong.go` / `nullstr.go` / `datetime.go` / `day.go` 这套自定义类型是有效的。

已证伪的一条见第 7 节（BigDecimal 尾零）。

### 仍存在的两处

| 项 | Java | Go | 证据 |
|---|---|---|---|
| `null` vs `""` | 未赋值的 `String` 输出 `null` | 输出 `""` | `getByTrailBo` 8 种 `stateType` × 22 字段 = 176 处；`changeTrailInfo` 的 `trailUuid`/`sectionCode` 同类 |
| HTML 转义 | `A<B>C&D` 原样输出 | **`A\u003cB\u003eC\u0026D`** | 回显实测：Java 字节 `plateKey":"A<B>C&D\"…`，Go 字节 `plateKey":"A\u003cB\u003eC\u0026D\"…`（`encoding/json` 默认 `SetEscapeHTML(true)`，gin `c.JSON` 走它） |

> 转义这条**差点漏掉**：差分工具是"解析后比语义"，`\u003c` 解析后与 `<` 相同，所以永远报 OK。
> 凡是按字节比对、算签名、做字符串去重的调用方会受影响。方法论教训见 `02` 第 1 节补充。

Java 侧**没有全局 Jackson 配置**（无 `spring.jackson.*`、无 `JacksonConfig`），
只有 54 处字段级 `@JsonFormat` —— Go 按字段复刻，这与"无全局配置"的事实一致。

## 4. Redis key 归属与分库后果

本轮实测确认的 key 状态（`redis db0=Java / db1=Go`）：

| key | 谁写 | db0 | db1 | 分库后果 |
|---|---|---|---|---|

| `car_list_jc` | 只读，靠运维写入（`Constants.java:285`；读点 `SysUtilController.java:123` 等 4 处） | 存在，17940 字节，**内含 `PARITY_UP_*` 合成车牌** | 不存在 | `carTrackQueryByTime`：Java `total=112`、Go 恒 0。**该值部分是历史测试注入的脏数据** |

| `DATE_*Capture:*`（5 类抓拍缓存） | 两端各自读写，含"查不到"的负缓存 | 有 | 有（含 `DATE_FeeRecord:AUDIT-SYNTHETIC-0001`） | Go 落空库时回源 DB，结果正确但多打一次 8 亿级表；负缓存**无 TTL**（Java `setCacheObject` 不带过期，Go `SetJSON(...,0)` 一致） |
| `car_curent_trail / car_history_trail / car_sync_time / trail:` | 两端各自写 | 有（含 `PARITY_UP_*`） | 有 | Go 的 `syncHistroyTrack` 读到空 → 恒走 `bannian` 分支、永不合并旧数据 |
| `pulsar:msg:processed:` / `pulsar:cdc:processed:` | 幂等标记，TTL 86400/604800 | Java 写 | Go 写 | 前缀相同、库不同 → **去重窗口互相独立**，同一 `dataId` 可能被两端各插一次 |
| `table:count:*` | `progressive` 分档读取 | 无 | 无 | 当前两端都回落配置值，实测 `s2-scalelevel` OK；但一旦运维只写 db0，Java 变档、Go 不变 |

### 4.1 依赖不可达的外部 Redis（存量风险）

`application.yml:139` `clusterNodes: <REDACTED-HOST>:22400`，`RedisSourceFactory` 用它建 JedisCluster。
实测**该地址不可达**；日志显示 `JedisCluster created successfully`（懒连接，创建不报错），
真正执行命令时才失败（`logs/…15:12:02.004 [scheduler-6] … JedisCluster created …` 紧跟任务结束）。
Java 与 Go 都受影响，非迁移引入，但会让"依赖这条通道的功能"静默降级。

## 5. 定时任务与双写风险

| 任务 | Java | Go | 写什么 | 备注 |
|---|---|---|---|---|

## 6. MQ 消费与生产

| | Java | Go |
|---|---|---|
| Kafka 消费者 | **无**（全仓 `@KafkaListener` 0 处） | 有（`internal/mq/kafka.go:66`，group `car-monit-go`） |
| RocketMQ 监听 | `RocketMqConsumer.java:19-24` 注解整体被注释 | — |
| RabbitMQ | 只声明队列，无 `@RabbitListener`/`@EnableRabbit` | `rabbitmq.enabled: false` |
| Pulsar | 真正的消费入口（`SnapshotFlowPulsarConsumer.java:120 @PostConstruct`、`DebeziumReadonlyPulsarConsumer.java:116`） | **Go 无 Pulsar 客户端**，把该角色映射到 Kafka |

要点：因为 Java 没有 Kafka 消费者，Go 用独立 group **不会抢 Java 的分区**；
但 Go 是当前唯一的 Kafka 消费端，会**独占消费**并写 DB/ES，而 Java 期望由自己的 Pulsar 链路产出同样的数据。
这属于架构选型差异，不是逐接口差异，但对"数据从哪来"有实质影响。

## 7. 复核后**证伪或降级**的审阅结论

代码审阅给出的下列结论，经我实测/读源码后不成立或需限定，**不进入问题清单**：

| 审阅初判 | 复核结果 |
|---|---|
| 「Go 的 HTTP 200 + `code:500` 与 Java 的 HTTP 500 全面不一致」 | **限定成立**：`large`/`unified` 两个 Controller 自己 catch 异常并返回 HTTP 200 + `code:500` 的 Map（`s2-stats-countfield` 实测 Java 就是这样），Go 在这两个 Controller 上**与 Java 一致**；真正的差异只在 19 个 base Controller |
| 「Go 把 `113.100` 序列化成 `113.1`，BigDecimal 标度丢失」 | **不成立**：实测两端 `startLon="113.1"`、`startLonDec=113.1` 完全相同 |
| 「Go 执行了 Java 已注释的 FeeRecord 回源，会多查数据」 | **代码层成立、行为层未显现**：`SysUtilServiceImpl.java:1028/1032/1036` 确为注释（已核实），Go 确实执行；但用真实 `pointUuid` 实测两端返回同样为空 → 降为 WARN |
| 「`/large/sync/*` 会覆盖 Java 写入的 ES 文档」 | 逻辑成立（Java 写 fastjson2 的 `_source`、Go 写自身模型 JSON，同 `_id` 会覆盖），但**本轮未执行这些写接口**（默认 `--allow-write` 关闭），属风险而非观测 |
| 「Go 缺少 Actuator 健康检查是缺陷」 | 反向：Java 根本没引 Actuator，Go 的 `/healthz` 是**新增能力**，不构成不等价 |

## 8. 配置项对照

`configs/config.yaml` 与 `application.yml` 键路径逐段对齐（Go 侧注释里标了源行号），
校验用的 `config.verify.yaml` 只改两处：`server.port: 9903`、`redis.database: 1`。

需要额外注意的**不是差异而是隐患**：`configs/config.yaml`（默认那份）里
`server.port: 9901` + `redis.database: 0` —— 一旦误用这份启动 Go，会和 Python 版抢 9901，
并且**直接写进 Java 的 db0**，把 Java 的字典缓存换成 Go 的格式，导致 Java 侧强转失败。
建议把这份文件的 redis 库号改成非 0，或删掉，避免误操作 → `04` P-ENV-3。
