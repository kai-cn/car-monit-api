## 3. 闭环审查新抓出的三个问题（都已修）

### A. 我自己引入的：`pageSize=0` 在 sysutil 路径退化成全表扫描

把 P-PAGE-2 改成"`pageSize<=0` → 空页"时，`crud.go` 加了 `if p.PageSize > 0` 保护，
但 `handler/sysutil.go` 的两个轨迹接口走的是另一条路：它把 `limit = offset + pageSize` 传给 repo，
而 **repo 约定 `limit<=0` 表示"不加 LIMIT"** —— 于是 `?pageSize=0` 从"给 10 行"变成"给全部行"。

| | 修复前 Go | Java | 修复后 Go |
|---|---|---|---|
| `GET /base/sysutil/carTrackQueryByTime?pageSize=0` | **1.83 MB / 8.4 s** | 55 B / 0.03 s（`total=112, rows=[]`） | **53 B / 0.0035 s** |

两个轨迹接口都已加保护并实测确认。教训：**同一套分页语义改到多条查询路径上时，
每条路径的"limit=0"约定都要单独确认**，差分工具默认的用例是 `pageSize=0` 只打在 CRUD 上，
所以没抓到 —— 已在 `suite.py` 里补上 sysutil 的边界用例。

### B. P-ID-1 此前只有代码改动，没有实测

补测确认：`snapshotflow`、`feeGantry` 两端返回的行 `id` 现在都是 32 位十六进制无横线。

### C. 三个修复只有代码走查、没有可执行证据

`P-FILT-5`（carNo AND carNoList）、`P-TRK-4`（时间窗上界）、`P-PAGE-4` 在 snapshotflow 上与
Repo 自身排序的优先级 —— 这三处当前**从 HTTP 层看不出来**（数据全在时间窗外 / 调用方不会同时传两者 /
不传 orderByColumn 时无差异）。新增 `internal/repo/zdata_trail_tracks_sql_test.go` 用源码文本断言锁住，
并做了反向验证（删掉 `extime <= now()` 后测试确实 FAIL），避免以后被"顺手优化"回退。

> **第三轮复核更正**：上面那句"删掉后测试确实 FAIL"对 `P-TRK-4` 成立，
> 对 `P-FILT-5` **不成立** —— 那条断言当时只在全文件里 grep 一个固定串
> `} else if utils.IsNotBlank(vo.CarNo)`，而真实的回退写法是 `} else if len(vo.CarNoList) > 0 {`，
> grep 不到，测试在 bug 存在时照样通过。已重写并逐条变异验证，见 `08` 第 2 节。
