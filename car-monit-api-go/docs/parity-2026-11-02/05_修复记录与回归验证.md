## 1. 拉平缓存状态：做法改了一次

第一次尝试是"往 Java 的 db0 补齐缓存"，**行不通**：本机还有共驻服务在周期性清库。

| 现象 | 证据 |
|---|---|
| `redis_equalize.py` 往 db0 写了 12 个 `sys_config:*` | 写完立即读到，Java 的 `snapshotflow total` 从 251 变 900 |
| 约 30 秒后 db0 的 `sys_config:*` **全部消失**，只剩一个 `sys_config:PARITY_config_6zd9d` | 用正确的 RESP 解析器观测（`raw/` 有脚本），连续两次 30s 采样均为 0 |
| 本机同时在跑的服务 | `:9988` `java -jar ruoyi-admin/target/ruoyi-admin.jar`、`:9989` `car-monit-backend-new\car-monit-go\bin\carmonit-server.exe`、`:9911` rust 版、`:9901` Python 版、`:9922` 未知 |

**改用反方向拉平**：只动 Go 自己的 db1，删掉 `sys_config:data_query`，让两端都走"缺省 → 受限分支"。
删除前已把原值备份到 `raw/db1-sys_config-data_query.bak.json`。

### 拉平后才暴露出来的重大缺陷

隔离期间 Go 的 `carTrackQueryByTime` 恒返回 0 行，把整条轨迹富集链路的问题全盖住了。拉平后：

| 观测项 | Java | Go（修复前） |
|---|---|---|
| 1223 个轨迹点里 `captureTime` 有值的数量 | **1188** | **0** |

根因：`internal/service/sysutil.go:211` 用 `time.ParseInLocation("2006-01-02T15:04:05", …)`，
Go 要求**整串消费完毕**，而真实数据是 `"2025-10-01T00:02:36.000+08:00"` → 报 `extra text: "+08:00"`；
Java 的 `new SimpleDateFormat("yyyy-MM-dd'T'HH:mm:ss").parse(...)`（`SysUtilServiceImpl.java:2037,2055`）
**只解析前缀、忽略尾部残留**，所以一直成功。
失败被 `if err == nil` 吞掉 → `CaptureTime` 恒空 → 下游 `mapTrailBoList` 的
`IsNotBlank(captureTime)` 永假（`service/sysutil.go:255`）→ **按时间去重/合并整段形同不存在**。

已修复，见下节 P-TRK-1。

### 过程中被测试抓到的两个自伤

1. `setByString` 处理指针时**先 `reflect.New` 分配、再递归**，递归失败即返回错误 —— 于是字段已经变成一个
   **非 nil 的零值**。如果这条字段是过滤条件，SQL 会带上 `= 零值`，比"忽略参数"更错。
   → 改为在调用前用 `supportsType()` 判定，从根上不进入分配分支。（`bind_test.go:TestBindQuerySkipsUnsupportedKind` 抓到）
2. `snapshotflow` repo 自带 `Order("snapshottime desc")`，而调用方排序被追加在它**之后** →
   `?orderByColumn=captureTime` 实际会被压住失效。→ 调整成调用方优先（`ods_rt_szdn_snapshot_flow_addcode.go`）。

### 一处有意偏离 Java 的选择

`orderByColumn` 非法值：Java 抛 `UtilException` 且无人 catch → **HTTP 500**；Go 回 **HTTP 400**（复用已有的 `BindError`，
响应体形状与 Spring 的参数转换错误一致）。理由是"参数非法"语义上属于请求错误，且 Go 已有对应机制。
已在代码注释与本文档登记，回归里 `P-ERR-1 注入拒绝` 一项即体现该差异（Java 500 / Go 400）。

## 4. 导出类实测（决策 ②，只跑导出、不跑同步）

`raw/export-probe.json`、`raw/export-probe-livedata.json`。

两端都能提交任务并返回同构的状态对象（键集合完全一致：`code/status/totalExported/filePartCount/submitTime/endTime`，
unified 多一个 `errorMessage`），`taskId` 都是 UUID，状态机都是 `RUNNING → FAILED`。

**但成功路径在本环境无法验证**：换用真实有数据的窗口（`2025-10-01 00:00~00:05`）后，
两端仍然都以 `Elasticsearch exception [all shards failed]` 失败。
ES 本身是活的（`snapshot_flow` 300 docs、`fee_records` 369、`trail_fitting` 1），
所以是导出用的 scroll/sort 与该索引 mapping 不匹配 —— **两端同因失败，属共享依赖问题，不是迁移差异**。
因此 `04` 里的 P-QRY-4（CSV 表头、排序方向、文件名与目录）仍停留在代码级结论，标为「待验证」。

实测到的两处确定差异（与代码审阅一致）：

| 项 | Java | Go |
|---|---|---|
| FAILED 时的 `endTime` | `0`（只在 COMPLETED 时赋值） | **写了真实时间戳** |
| `errorMessage` | ES 原始异常串 | 前面加了 `"开始 scroll 失败: "` |

`POST /large/sync/full|incremental|repair` 按约定**未执行**（会用同 `_id` 覆盖 Java 写入的 ES `_source`）。
