# 02 差分实测结果（Java :9902 ↔ Go :9903）

工具：`tools/parity.py` + `tools/suite.py` + `tools/suite2.py`。
第一轮 **358 条**用例（`raw/full-asis.jsonl`、`raw/full-asis.md`），第二轮 **29 条**补测
（`raw/probe2.json`），每条用例的完整报文在 `raw/<用例id>.java.http` / `.go.http`。

## 1. 方法（为什么不能直接对打两端）

| 措施 | 原因 |
|---|---|
| 用例参数**由 Java 真实响应自我派生**（取首行字段当过滤值） | 凭空编的过滤条件查不到东西，「两端都返回空」会被误判成一致 |
| 列表**按真实主键对齐**后逐字段比 | 多数 mapper XML 没有 ORDER BY，按行号比会把顺序差异报成内容差异 |
| 差异出现时**再打一次 Java**，Java 与自己不一致 → 判 `NONDET` | 两端共用一个库且调度任务在写数据；先证明基准可复现，才能把差异归因到 Go |
| 大列表截断到前 N 行，但**先记录全长** | 把「长度差」和「内容差」分开，否则 1526 行只报成"整行不同" |
| 写操作过重的端点用 **405 探针**（POST 一个 GET 路由）只验存在性 | 避免在共用库上触发全量同步，把被测数据本身改掉 |

判定含义：`OK` 等价 ｜ `DIFF` 响应内容不同 ｜ `STATUS` HTTP 状态码不同 ｜ `NONDET` 基准端自身不可复现（不计入 Go 缺陷）。

## 3. 系统性差异（影响面最大，按危害排序）

### A. `pageSize` 被 Go 截到 1000 —— 数据静默丢失【最严重】

`internal/handler/bind.go:196`：`if p.PageSize > 1000 { p.PageSize = 1000 }`，Java 侧无上限。

| 用例 | Java | Go |
|---|---|---|
| `gantry-full-set`（`pageSize=1526`，全表 1526 行） | 1526 行 | **1000 行**（`ONLY_JAVA` 528 项） |
| `gantry-list-bigpagesize`（`pageSize=5000`） | 1526 行 | **1000 行** |
| `gantryIp-full-set`（1033 行） | 1033 | **1000**（缺 33） |
| `trailtracks-full-set`（1379 行） | 1379 | **1000**（缺 379） |

**实测复现 3 张表**（`gantry` 1526 行、`trailtracks` 1379 行、`gantryIp` 1033 行 —— 即所有行数超过 1000 的表）。
其余 15 张表因为总量 <1000 没触发，但风险等价。调用方写 `pageSize=2000` 拉全量时，
Go 少给一半且**不报错、不提示**，`total` 仍是全量数，前端会以为"还有下一页"而永远翻不到。

### B. `pageSize=0` / `-1` 语义相反

`bind.go:193-195` 把非法/非正值回落成默认 10；Java（PageHelper）返回**空集**。

```
fwqjcxx-list-pagesize0   GET /base/fwqjcxx/list?pageNum=1&pageSize=0   Java rows=0   Go rows=10
```
**19 张表 × 2 条用例 = 38 条全部复现**，无一例外。

### C. 翻页越界：Java 回夹末页，Go 返回空集

Java `PageDomain.reasonable` 默认 `true`（`TableSupport.java:36`），`pageNum` 超界时 PageHelper 回夹到最后一页；
Go `crud.go` 的 `pageSlice` 直接给空。

```
gantry-list-farpage      GET /base/gantry/list?pageNum=99999&pageSize=5   Java rows=1（末页）  Go rows=0
fwqjcxx-list-farpage     同上                                            Java rows=3            Go rows=0
```
**17 张表复现**（另 2 张落在 NONDET 里，未计入）。

### D. `orderByColumn` / `isAsc` Go 完全忽略

`bind.go:187` 明确写着"未实现"（理由是 SQL 注入风险）。Java 侧 `PageUtils.java:23-25` 会拼进 ORDER BY。

```
fwqjcxx-list-order  ?orderByColumn=agentPk&isAsc=desc
   Java → agentPk 244,245,246,247,248（降序）
   Go   → agentPk 1,15,…（无序，等于没收到该参数）
```
**17 张表复现**（行集完全不同）。这是"接口没报错但内容不对"的典型。

> Go 的安全顾虑成立，但 Java 侧也不是没防护：`SqlUtil.java:31-42` 用白名单正则校验，
> 非法字符直接抛 `UtilException`（`vehicleweight-list-order` 实测 Java 500 就是这个）。
> 所以「拒绝非法排序」而非「忽略排序」才是与基准等价的做法。

### E. 过滤条件缺失（Go 侧）

机械对照 Java mapper XML 的 `<if>` 列 与 Go repo 的 `tx.Where` 列：`tools/predicates.py`，
**19 张表里 15 张完全一致**，问题集中在 3 张：

| 表 | Java 过滤列 | Go 实现 | 实测证据 |
|---|---|---|---|
| `zdata_trail_tracks` | 7 个（uuid,type,point_count,plate_key,enter_time,exit_time,trail_points） | **只做 3 个**，且 `enter_locationcode`/`exit_locationcode` 是 Java 列表查询里没有的 | `trailtracks-filter-type`：Java `total=879`（生效）↔ Go `total=1379`（未过滤）；`filter-pointCount`：Java 2 行 ↔ Go 5 行 |
| `dwd_lczt_fwqjcxx` | 33 个（但其中 28 个引用的是 SELECT 别名，见 F 类） | 只实现 6 个真实列 | `fwqjcxx-filter-agentPk`：Java 500 ↔ Go 200 |
| `ods_lwzxsfsj_fee_records01` | Java 侧根本没有 list 语句 | Go 自造 13 个过滤列 | `feerecords-*`：Java 全组 500 |

> Go 侧丢过滤条件是**静默**的：`bind.go:57` `_ = setByString(...)` 忽略绑定错误，
> `*Timestamp` / 自定义类型走 `default:` 分支直接跳过。参数名拼错、类型不接受，都是"当作没传"。

### F. Java 基准自身坏掉的三处（不能要求 Go 复刻）

| 端点 | 根因（代码级） | Java 实测 | Go 实测 |
|---|---|---|---|
| `/base/feerecords/*` | `OdsLwzxsfsjFeeRecords01Mapper.xml` 只定义了 `selectByCursorShard`，**没有** `selectOdsLwzxsfsjFeeRecords01List` → MyBatis `BindingException: Invalid bound statement (not found)`（`logs/pro-business-api-2026-11-02.1.log:39105`） | HTTP 500（9 条用例全中） | 200 + 1016 行 |
| `/base/fwqjcxx/list?任意过滤` | `DwdLcztFwqjcxxMapper.xml:43` 是 `t.id agent_pk`（别名），`:76` 却写 `and t.agent_pk = #{agentPk}` —— WHERE 不能引用 SELECT 别名 → 列不存在 | HTTP 500 | 200（该 28 个参数被 Go 忽略） |
| `/base/sysutilTest/syncOdsSzdnGantry`、`syncSuspiciousCar1..10` | `selectGantryNum` / `selectOdsLwzxsfsjFeeRecords01ListNew` 只有接口声明、无 SQL（同 BindingException） | HTTP 500 | 501（明确标注未移植） |
| `/base/vehicleweight/list?任意过滤` | 同类别名问题 + `orderByColumn=uuid` 触发 `SqlUtil` 白名单异常 | HTTP 500 | 200 |

**这解释了 27 条 STATUS 中的绝大多数**。结论：Go 在这些点上"比 Java 能用"，但**行为不等价**，
切换时调用方会看到"以前 500 现在 200"，需要产品侧确认是保留还是修复 Java。

### G. 时间格式决定"查 ES 还是查库"（查询族最大风险）

Java `UnifiedQueryService.java:197` 用 `Timestamp.valueOf()`，只吃 `yyyy-MM-dd[ HH:mm:ss]`；
Go `model/day.go:117-126` 接受 8 种格式 + epoch 毫秒。同一请求会落到**不同存储**：

| 输入 | Java | Go |
|---|---|---|
| `startTime=2025-10-01`（只有日期） | 解析失败 → 走 ES → **0 行** | 解析成功 → 走 GaussDB → **2 行**（`s2-large-dateonly`） |
| `startTime=2025-10-01 00:00:00` | 200 | 200 ✅ 一致（`s2-large-fullfmt` OK） |
| `startTime=2025/10/01` | 0 行 | 2 行（`s2-large-slash`） |
| `startTime=1759248000000`（epoch） | 200 + `data:[]` | **`code:500` + 原始 GaussDB 错误文本**（`s2-large-epoch`） |

最后一行还要额外记一条：Go 把 `ERROR: invalid input syntax for type timestamp` 直接回给客户端，
属于**内部错误外泄**（Java 在这条路径上是 catch 后返回空集）。

### H. 模糊匹配词表不一致

Java `LargeScaleQueryService.java:235-239` 的 term 词表是 `platenumber/vehicleplate/gantrycode/sectioncode/envehicleid`，
Go `query.go:297` 只有 `platenumber/gantrycode/sectioncode`。≥7 位车牌在 Java 走 `term(.keyword)`、Go 走 `match(.ngram)`：

```
s2-fuzzy-long  /api/v1/large/fee?platenumber=粤DZW906   Java 0 行   Go 2 行
```

### I. 参数校验宽严不同（Java 400 / Go 200）

第二轮实测新增 5 条，全部同一形状 —— Go 缺必填校验与类型校验：

| 用例 | 请求 | Java | Go |
|---|---|---|---|
| `s2-stats-nofield` | `stats/group` 不带 `groupBy` | 400 | 200 + `code:500` |
| `s2-stats-badtopn` | `topN=abc` | 400 | 200（回落 100） |
| `s2-large-car-noarg` | `large/carTrackQueryByCarNo` 不带 `carNo` | 400 | 200 |
| `s2-large-pagesize-str` | `pageSize=abc` | 400 | 200（回落默认） |
| `s2-endtype-int` | `endTime=2025-10-02 00:00:00`（该字段是 Integer） | 400 | 200（静默忽略） |
| `crosscut-bad-json-post` | POST 非法 JSON 体 | 400 | **200** |
| `crosscut-empty-post` | POST 空体 | 400 | **200** |

`stats/group` 另有：`topN=0` 或 `countField` 指定时 Java 返回 `code:500`
（`Elasticsearch exception [all shards failed]`），Go 返回 `code:200, data:{}` —— 一个报错一个给空集。

### J. 错误信封结构不同（状态码一致，body 不一致）

| | Java | Go |
|---|---|---|
| 404 | `{"timestamp","status":404,"error":"Not Found","message":"","path"}` | `{"code":404,"msg":"接口不存在: GET /x"}` |
| 405 | Spring 错误体 + `Allow` 头 | `{"code":405,"msg":"请求方法不支持: POST"}`，**无 `Allow`** |
| 未捕获异常 | HTTP 500 + Spring 错误体 | **HTTP 200** + `{"code":500,"msg":…}` |

注意第三行：`large`/`unified` 两个 Controller 自己 catch 了异常并返回 `code:500` 的 Map（HTTP 200），
Go 的"HTTP 200 + code:500"在这两个 Controller 上**反而与 Java 一致**；
差异只在 19 个 base Controller（Java 不 catch → HTTP 500）。
这一条纠正了代码审阅阶段的初判，是以实测为准的结果。

### K. 结尾斜杠

`crosscut-trailing-slash`：`GET /base/gantry/list/?pageSize=1` → **Java 200，Go 404**。
Go `router.go:76` 显式关了 `RedirectTrailingSlash`（注释写"与 Spring 一致：不自动改写"），
但 Spring 的 `AntPathMatcher` 实际**容忍**结尾斜杠。已配置 `matching-strategy: ant_path_matcher`
（`application.yml:9-10`），所以这是 Go 侧的判定错误 → 会 404 掉真实存在的调用。

### L. `null` vs `""` 序列化（sysutil 组）

`TrailBo` / `TrailInfo` 里所有未赋值的 `String`：Java 输出 `null`，Go 输出 `""`。
`getByTrailBo` 的 8 种 `stateType` × 22 个字段 = **176 处**，实测每条用例都是 22 项 NULLISH。
`changeTrailInfo` 的 `trailUuid`、`sectionCode` 同类。

> 影响取决于调用方是否写 `if (x === null)`。Java 侧 `CommonUtil.isNull()` 把 null 和 "" 一视同仁，
> 所以后端之间没差；**前端判断 `x != null` 会由 false 变 true**，属可见回归。

## 4. NONDET 的 22 条怎么读

集中在 `feeGantry`(11) 与 `snapshotflow`(11)。两个原因叠加：

1. 这两张表在**被持续写入**（Java 与 Go 的调度任务都在跑，`TrackTask` 每 3 分钟、`DataFlowTask` 每 1/5 分钟）；
2. Go 的 `snapshotflow` repo 加了 `Order("snapshottime desc")`（`repo/ods_rt_szdn_snapshot_flow_addcode.go:100`），
   而 Java 的 `selectOdsRtSzdnSnapshotFlowAddcodeList` **没有 ORDER BY**（48 个 `<if>`，实测该 select 内无 order by）。

所以同一页 Java 每次取到的行都可能不同 —— **不能把这类差异记为 Go 缺陷**，但也不能忽略：
Java 无 ORDER BY 配 PageHelper 分页本身就是缺陷（翻页漏行/重行），Go 补了排序是修正方向，
代价是"首页内容"与 Java 不逐行相同。需要产品侧确认以哪端为准 → `04` P-ORDER-1。

## 5. 环境与状态造成的差异（不是代码缺陷，但会让对比失真）

两端 Redis 分库（Java db0 / Go db1）后，有两类 key **只有 Java 侧有**：

| key | db0 | db1 | 后果 |
|---|---|---|---|
| `sys_config:*`（含 `data_query`） | **无**（`KEYS sys_config*` 返回空） | 有 `data_query="queryall"`（Go 的字典任务从库里的 `sys_config` 表刷进去的） | Java 走"非 queryall"分支 → `snapshotflow` `total=251`；Go 走 queryall → `total=900`。同库同 SQL，结果差 3.6 倍 |
| `car_list_jc`（重点车列表） | 有 | **无**（Java 代码只读不写，靠运维写入） | `carTrackQueryByTime`：Java `total=112`，Go **恒为 0**。该接口在 Go 单独部署且未同步该 key 时功能不可用 |

还有第三类：Java `application.yml:139` 配了 `clusterNodes: 36.200.31.15:22400`（`RedisSourceFactory` 的 JedisCluster），
实测**该地址不可达**。`RedisCache`（`spring.redis` → 127.0.0.1:6379 db0）与这条集群通道是两套路径，
本轮所有对比走的是前者；但依赖集群通道的代码路径在任何一端都是"运行期失败"，属存量风险 → `04` P-ENV-4。

**结论**：这 3 项在跑对比前应当拉平，否则测出来的"差异"其实是环境差异。
是否要往 Java 的 db0 写入与 Go db1 等价的 `sys_config` / `car_list_jc`（可逆，写完可删）
属于对运行中服务的写操作，需业主确认 → 见 `04` 第 0 节"待决策"。

## 6. 第二轮补测把哪些初判证伪了

| 代码审阅初判 | 实测结论 |
|---|---|
| 「Go 用 `FormatFloat` 丢掉 BigDecimal 尾零，`113.100` 会变 `113.1`」 | **不成立**：两端都输出 `startLon="113.1"`、`startLonDec=113.1`（`s2-change-scale` 仅 `sectionCode` 的 null/"" 一处差）。Java 侧 `new BigDecimal(...)` 的值也被 `changeData` 覆写，标度差异不存在 |
| 「Go 的 `changeTrailInfo` 对非法入参返回 HTTP 200」 | 成立但需限定：**Java 的 `large`/`unified` Controller 同样返回 HTTP 200 + `code:500`**，真正的 HTTP 500 差异只出现在 19 个 base Controller 上 |
| 「Go 执行了 Java 已注释掉的 FeeRecord/FeeStationEnter/FeeStationExit 回源，会多查数据」 | **代码层成立**（`SysUtilServiceImpl.java:1028/1032/1036` 确为 `//` 注释），但用真实 `pointUuid` 实测**未见结果差**（`s2-gbt-FeeRecord` 两端同样空），因为 Go 的回源没命中数据。记为 WARN 而非 BLOCK |
