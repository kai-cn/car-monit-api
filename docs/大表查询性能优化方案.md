# 大表查询性能优化方案

## 一、背景

### 1.1 涉及表

| 表名 | 接口 | 时间查询字段 | 通用查询字段（支持全模糊） |
|------|------|-------------|--------------------------|
| `ods_rt_szdn_snapshot_flow_addcode` | /base/snapshotflow/list | snapshottime（抓拍时间） | platenumber, orgname, sectionname, roadname, gantryname, tollname |
| `ods_lwzxsfsj_fee_records_01` | /base/feerecords/list | transtime（交易时间） | platenumber, orgname, sectionname, roadname, gantryname, tollname |
| `zdata_trail_fitting` | /carTrackQueryByCarNo | extime（出站时间） | platenumber |

### 1.2 数据量

| 维度 | 数值 |
|------|------|
| 日增 | 70 万条/表 |
| 月增 | 2000 万条/表 |
| 3 年累计 | ~8 亿条/表 |
| 3 张表合计 | ~24 亿条 |

### 1.3 查询场景

- 时间范围查询（最长 1 年）
- 通用字段全模糊查询（LIKE '%xxx%'）
- 数据导出
- 统计分析

## 二、为什么不建议分库分表

### 2.1 数据量评估

| 指标 | 数值 |
|------|------|
| 单表 3 年行数 | ~8 亿 |
| 单行（查询返回字段） | ~200 bytes |
| 纯数据 | ~160 GB |
| 索引 | ~80 GB |
| 单表总大小 | ~240 GB |
| 3 张表合计 | ~700 GB |

PostgreSQL 单表上限在 TB 级别，240 GB 配合按月分区（每个分区 ~6.7 GB）完全在舒适区内，**不需要分库分表**。

### 2.2 分库分表的代价

| 问题 | 说明 |
|------|------|
| 跨库 JOIN | 收费流水表 JOIN 元数据表 `ods_szdn_gantry` 无法执行，需要每个库复制一份（广播表） |
| 跨库排序 | `ORDER BY time DESC` 需中间件做二次归并排序，性能差 |
| 跨库分页 | `LIMIT 10 OFFSET 10000` 需从每个库取大量数据再汇总，OFFSET 越大越慢 |
| 跨库聚合 | COUNT/SUM/AVG 需查询所有分片再汇总 |
| 扩容迁移 | hash 取模分片下，加节点需要全量数据迁移 |
| 运维复杂度 | 分布式事务、数据一致性、中间件维护 |

### 2.3 结论

**使用 PostgreSQL 原生分区 + Elasticsearch 混合架构**，避免分库分表。

```
│  ┌──────────┐  ┌──────────┐  ┌────────────────┐  │
│  │PostgreSQL│  │Elasticsearch│ │ Elasticsearch  │  │
│  │ 按月分区  │  │ ngram索引  │  │ PIT + 聚合     │  │
```

**路由策略：**

| 查询类型 | 目标 | 说明 |
|----------|------|------|
| 精确车牌 + 7 天内 | PostgreSQL | 时间范围小，B-tree 索引高效 |
| 精确车牌 + 超过 7 天 | Elasticsearch | 时间范围大，ES 倒排索引更快 |
| 全模糊查询 LIKE '%xxx%' | Elasticsearch | pg_trgm 在 8 亿行上扛不住 |
| 统计/聚合 | Elasticsearch | ES aggregation 分布式聚合 |
| 导出 | Elasticsearch | PIT + search_after 游标 |

## 四、PostgreSQL 分区方案

### 4.1 分区策略

**三张表统一按月分区（RANGE PARTITION BY 时间字段）：**

| 表 | 分区键 | 分区粒度 | 3 年分区数 | 单分区大小 |
|----|--------|----------|-----------|-----------|
| ods_rt_szdn_snapshot_flow_addcode | snapshottime | 月 | 36 | ~6.7 GB |
| ods_lwzxsfsj_fee_records_01 | transtime | 月 | 36 | ~6.7 GB |
| zdata_trail_fitting | extime | 月 | 36 | ~6.7 GB |

> **不要按小时或按日分区。** 按小时分区 3 年产生 26280 个分区，PostgreSQL 分区元数据管理开销巨大。按月分区，一年查询只扫描 12 个分区，分区裁剪效率最高。

### 4.2 分区 DDL（示例）

```sql
-- 抓拍流水表
CREATE TABLE jl_data01.ods_rt_szdn_snapshot_flow_addcode (
    -- ... 所有字段 ...
) PARTITION BY RANGE (snapshottime);

-- 创建分区（2026年1月）
CREATE TABLE jl_data01.ods_rt_szdn_snapshot_flow_addcode_202601
    PARTITION OF jl_data01.ods_rt_szdn_snapshot_flow_addcode
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

-- 创建分区（2026年2月）
CREATE TABLE jl_data01.ods_rt_szdn_snapshot_flow_addcode_202602
    PARTITION OF jl_data01.ods_rt_szdn_snapshot_flow_addcode
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

### 4.3 分区自动管理

```sql
-- 自动创建下月分区（每月执行一次）
CREATE OR REPLACE FUNCTION create_next_month_partitions()
RETURNS VOID AS $$
DECLARE
    next_month DATE := date_trunc('month', CURRENT_DATE)::DATE + INTERVAL '1 month';
    part_name TEXT;
BEGIN
    part_name := 'ods_rt_szdn_snapshot_flow_addcode_' || TO_CHAR(next_month, 'yyyymm');
    EXECUTE format(
        'CREATE TABLE IF NOT EXISTS jl_data01.%I
         PARTITION OF jl_data01.ods_rt_szdn_snapshot_flow_addcode
         FOR VALUES FROM (%L) TO (%L)',
        part_name, next_month, next_month + INTERVAL '1 month'
    );
    -- 同样处理另外两张表...
END $$ LANGUAGE plpgsql;

-- 定时任务：pg_cron 每月1号执行
-- SELECT cron.schedule('create-partitions', '0 0 1 * *', 'SELECT create_next_month_partitions();');
```

```sql
-- 删除过期分区（保留最近 13 个月）
CREATE OR REPLACE FUNCTION drop_old_partitions(months_to_keep INTEGER DEFAULT 13)
RETURNS INTEGER AS $$
DECLARE
    cutoff_date DATE := CURRENT_DATE - (months_to_keep || ' months')::INTERVAL;
    part_name TEXT;
    drop_count INTEGER := 0;
BEGIN
    FOR part_name IN
        SELECT tablename FROM pg_tables
        WHERE schemaname = 'jl_data01'
          AND tablename ~ '^ods_rt_szdn_snapshot_flow_addcode_\d{6}$'
    LOOP
        IF TO_DATE(SUBSTRING(part_name FROM '\d{6}$'), 'yyyymm') < cutoff_date THEN
            EXECUTE format('DROP TABLE IF EXISTS jl_data01.%I', part_name);
            drop_count := drop_count + 1;
        END IF;
    END LOOP;
    RETURN drop_count;
END $$ LANGUAGE plpgsql;
```

## 五、索引方案

### 5.1 索引策略

| 索引类型 | 用途 | 适用场景 |
|----------|------|----------|
| B-tree（时间字段） | 时间范围查询 + 分区裁剪 | 所有查询 |
| B-tree（时间 + 编码字段） | 时间 + 等值过滤 | 精确查询 |
| GIN + pg_trgm | 全模糊查询 LIKE '%xxx%' | 模糊查询辅助 |
| 覆盖索引（INCLUDE） | 避免回表 | 高频查询字段 |

### 5.2 抓拍流水表索引

```sql
-- 启用扩展
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- 时间范围索引（分区裁剪核心）
CREATE INDEX IF NOT EXISTS idx_snapshot_time
    ON jl_data01.ods_rt_szdn_snapshot_flow_addcode (snapshottime DESC);

-- 时间 + 门架编号联合索引
CREATE INDEX IF NOT EXISTS idx_snapshot_time_gantry
    ON jl_data01.ods_rt_szdn_snapshot_flow_addcode (snapshottime DESC, gantrycode);

-- 时间 + 路段编号联合索引
CREATE INDEX IF NOT EXISTS idx_snapshot_time_section
    ON jl_data01.ods_rt_szdn_snapshot_flow_addcode (snapshottime DESC, sectioncode);

-- 时间 + 管理中心编号联合索引
CREATE INDEX IF NOT EXISTS idx_snapshot_time_org
    ON jl_data01.ods_rt_szdn_snapshot_flow_addcode (snapshottime DESC, orgcode);

-- 覆盖索引（避免回表）
CREATE INDEX IF NOT EXISTS idx_snapshot_covering
    ON jl_data01.ods_rt_szdn_snapshot_flow_addcode
    (snapshottime DESC, gantrycode, sectioncode)
    INCLUDE (platenumber, datauuid, platetypecode);

-- 车牌号精确匹配 B-tree
CREATE INDEX IF NOT EXISTS idx_snapshot_plate_btree
    ON jl_data01.ods_rt_szdn_snapshot_flow_addcode (platenumber);

-- 车牌号模糊匹配 GIN（仅作为 ES 不可用时的降级方案）
CREATE INDEX IF NOT EXISTS idx_snapshot_plate_trgm
    ON jl_data01.ods_rt_szdn_snapshot_flow_addcode
    USING GIN (platenumber gin_trgm_ops);

-- 门架名称模糊匹配 GIN
CREATE INDEX IF NOT EXISTS idx_snapshot_gantry_name_trgm
    ON jl_data01.ods_rt_szdn_snapshot_flow_addcode
    USING GIN (gantryname gin_trgm_ops);
```

### 5.3 收费流水表索引

```sql

    ON jl_data01.ods_lwzxsfsj_fee_records_01 (transtime DESC);

    ON jl_data01.ods_lwzxsfsj_fee_records_01
```

### 5.4 轨迹表索引

```sql
CREATE INDEX IF NOT EXISTS idx_trail_extime
    ON jl_data01.zdata_trail_fitting (extime DESC);

CREATE INDEX IF NOT EXISTS idx_trail_plate
    ON jl_data01.zdata_trail_fitting (envehicleid);

CREATE INDEX IF NOT EXISTS idx_trail_time_plate
```

### 5.5 索引效果预估

| 查询场景 | 推荐索引 | 预期提升 |
|----------|----------|----------|
| 完整车牌精确匹配 | B-tree | 10-100x |
| 车牌模糊查询 LIKE '%赣A1%' | GIN (pg_trgm) | 20-50x |
| 时间范围查询 | B-tree + 分区裁剪 | 5-20x |
| 时间 + 门架编号 | 联合索引 B-tree | 10-30x |
| 覆盖索引避免回表 | INCLUDE 子句 | 2-3x |

## 六、Elasticsearch 方案

### 6.1 为什么需要 ES

pg_trgm GIN 索引在 8 亿行上的全模糊查询仍然需要扫描大量索引条目，延迟在秒级甚至十秒级。ES 的倒排索引 + ngram 分词才是全模糊查询的正解。

### 6.2 索引映射

```json
{

    "number_of_shards": 5,
    "number_of_replicas": 1,
    "refresh_interval": "5s",
    "analysis": {
      "analyzer": "ngram_analyzer",
      "tokenizer": "ngram_tokenizer"
    },
    "tokenizer": {
      "ngram_tokenizer": {
        "type": "ngram",
        "min_gram": 2,
        "max_gram": 4
      }
    }
  },
  "mappings": {
    "properties": {
      "platenumber": {
        "type": "text",
        "analyzer": "ngram_analyzer",
        "fields": {
          "keyword": { "type": "keyword" }
        }
      },
      "gantryname": {
        "type": "text",
        "analyzer": "ngram_analyzer",
        "fields": {
          "keyword": { "type": "keyword" }
        }
      },
      "orgname": {
        "type": "text",
        "analyzer": "ngram_analyzer",
        "fields": {
          "keyword": { "type": "keyword" }
        }
      },
      "sectionname": {
        "type": "text",

          "keyword": { "type": "keyword" }
```

### 6.3 生命周期管理（ILM）

```
hot  (0-30天)  : 5 shards, 1 replica, 热节点
warm (30-90天)  : shrink → 1 shard, 温节点
cold (90-365天)  : freeze, 冷节点
delete (>365天)  : 自动删除
```

### 6.4 数据同步策略

| 模式 | 触发方式 | 说明 |
|------|----------|------|
| 增量同步 | 定时任务（每分钟） | Redis 水位标记，拉取新数据，BulkProcessor 批量写入 |
| 全量同步 | 手动触发 | 按时间分片并行读取，keyset 游标分页，1000 条/批 |
| 修复同步 | 手动触发 | 指定时间窗口重新同步 |

## 七、查询优化

### 7.1 强制时间范围

```java
// 不允许无时间范围的查询
if (startTime == null || endTime == null) {
    throw new BusinessException("时间范围为必填项");
}

// 时间范围不超过 1 年
if (ChronoUnit.DAYS.between(startTime, endTime) > 365) {
    throw new BusinessException("查询时间范围不能超过一年，请缩小范围");
}
```

### 7.2 深分页限制

```java
// OFFSET 超过 10000 拒绝，提示缩小查询范围
if (pageNum * pageSize > 10000) {
    throw new BusinessException("查询结果过多，请缩小查询条件后重试");
}
```

### 7.3 游标分页（替代 OFFSET）

```sql
-- 替代 LIMIT 100 OFFSET 10000
-- 使用 keyset pagination：
SELECT * FROM ods_rt_szdn_snapshot_flow_addcode
WHERE snapshottime >= '2026-01-01' AND snapshottime < '2026-02-01'
  AND (snapshottime, datauuid) > ('2026-01-15 10:30:00', 'uuid-xxx')
ORDER BY snapshottime ASC, datauuid ASC
LIMIT 100;
```

### 7.4 查询路由策略

```java
// 精确车牌 + 7天内 → PostgreSQL
if (isExactPlate(plateNumber) && daysBetween(start, end) <= 7) {
    return queryFromPostgreSQL(params);
}

// 全模糊查询 → Elasticsearch
if (hasFuzzyCondition(params)) {
    return queryFromElasticsearch(params);
}

// 超过 30 天 → Elasticsearch
if (daysBetween(start, end) > 30) {
    return queryFromElasticsearch(params);
}

// 默认 → PostgreSQL
return queryFromPostgreSQL(params);
```

## 九、统计优化

### 9.1 预聚合表（推荐）

```sql
-- 每小时统计表
CREATE TABLE jl_data01.stats_snapshot_hourly (
    stat_hour TIMESTAMP,
    orgcode VARCHAR(32),
    sectioncode VARCHAR(32),
    gantrycode VARCHAR(32),
    pass_count BIGINT,
    unique_plate_count BIGINT,
    PRIMARY KEY (stat_hour, orgcode, sectioncode, gantrycode)
);

-- 定时任务：每小时聚合一次
INSERT INTO jl_data01.stats_snapshot_hourly
SELECT
    date_trunc('hour', snapshottime) AS stat_hour,
    orgcode, sectioncode, gantrycode,
    COUNT(*) AS pass_count,
    COUNT(DISTINCT platenumber) AS unique_plate_count
FROM jl_data01.ods_rt_szdn_snapshot_flow_addcode
WHERE snapshottime >= date_trunc('hour', NOW() - INTERVAL '2 hours')
  AND snapshottime < date_trunc('hour', NOW())
GROUP BY 1, 2, 3, 4;
```

## 十一、附录：分区键选择总结

**为什么用时间字段而不是车牌号做分区键？**

| 对比维度 | 时间分区 | 车牌号分区 |
|----------|----------|------------|
| 查询路由 | 查询都带时间范围，精准路由到指定分区 | 需要扫描所有分区 |
| 分区裁剪 | 一年查询只扫 12 个分区 | 无法裁剪 |
| 写入热点 | 当月分区有热点，但可接受（2000 万/月） | 均匀分布 |
| 扩容 | 按月追加，无需迁移 | 取模分片，加节点需全量迁移 |
| 数据清理 | DROP 过期分区，秒级 | 需要 DELETE，极慢 |

**结论：时间字段是最佳分区键。** 所有查询都带时间范围条件，这是最高效的分区裁剪策略。2000 万/月的写入量对 PostgreSQL 而言不存在热点问题。
